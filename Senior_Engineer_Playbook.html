PHP & Laravel
PHP 8 — the language a senior is expected to write today
25m
Picture it like this

Think of enums like a fixed menu in a restaurant. With string constants, a waiter can scribble any dish name — including ones the kitchen can't cook. With an enum, only real menu items can be ordered, and each dish knows its own price and cooking rules (methods on the enum). readonly is a sealed envelope: once written and sealed, nobody can change what's inside.

enum হলো রেস্টুরেন্টের নির্দিষ্ট মেনুর মতো — মেনুর বাইরের কোনো খাবার অর্ডারই করা যায় না, আর প্রতিটি খাবার নিজের দাম-নিয়ম নিজেই জানে। readonly হলো সিল করা খামের মতো — একবার লিখে বন্ধ করলে আর বদলানো যায় না।

ধারণাটি সংক্ষেপে

PHP ৮-এর নতুন ফিচারগুলো কঠিন কিছু নয়, কিন্তু ইন্টারভিউয়ার এগুলো দিয়ে বোঝেন আপনি আপডেটেড কিনা। সবচেয়ে গুরুত্বপূর্ণ চারটি: enum দিয়ে স্ট্যাটাসের মতো নির্দিষ্ট মানগুলো টাইপ-নিরাপদ করা যায় এবং ভেতরে মেথডও রাখা যায়; readonly প্রপার্টি দিয়ে DTO বা Money-র মতো অবজেক্ট সত্যিকারের অপরিবর্তনীয় করা যায়; constructor promotion দিয়ে অনেক কোড কমে; আর match হলো switch-এর উন্নত রূপ — এটি strict, মান রিটার্ন করে, এবং কোনো কেস না মিললে এরর দেয়। ইন্টারভিউতে ফিচারের তালিকা না দিয়ে বলুন এগুলো আপনার ডেটা মডেলিং কীভাবে বদলেছে।

Modern PHP is a typed, expressive language and interviewers use your feature vocabulary as a proxy for how current you are. Four things carry most of the weight.

Enums (8.1) replace class constants for any fixed set — order status, user role, payment state. Unlike constants they are a real type, so an invalid value cannot reach your domain. They can hold methods, so behaviour lives beside the value instead of scattered across if-statements, and they can implement interfaces.

Readonly properties (8.1) and readonly classes (8.2) give you genuine immutability. Assign once in the constructor, never again. This is what makes DTOs and value objects trustworthy — a Money object that cannot be mutated after creation removes an entire class of bug.

Constructor property promotion (8.0) collapses the declare-then-assign boilerplate into the signature. Every service class you write gets shorter.

match (8.0) is switch done properly: strict comparison, returns a value, no fallthrough, and throws if nothing matches rather than silently doing nothing.

Also know: named arguments, the nullsafe operator, union and intersection types, never as a return type, and first-class callable syntax. In 8.3, typed class constants and json_validate().

The thing that separates a senior answer from a junior one is not listing these. It is explaining what each one changed about how you model data.

Example
<?php
enum OrderStatus: string {
    case Pending   = 'pending';
    case Paid      = 'paid';
    case Cancelled = 'cancelled';

    public function canRefund(): bool {
        return $this === self::Paid;
    }
}

final class Money {
    public function __construct(
        public readonly int $minorUnits,   // 1050 = 10.50
        public readonly string $currency,
    ) {}

    public function add(Money $other): self {
        if ($other->currency !== $this->currency) {
            throw new InvalidArgumentException('Currency mismatch');
        }
        return new self($this->minorUnits + $other->minorUnits, $this->currency);
    }
}

$fee = match($status) {
    OrderStatus::Pending   => new Money(0, 'BDT'),
    OrderStatus::Paid      => new Money(250, 'BDT'),
    OrderStatus::Cancelled => throw new LogicException('Cancelled orders have no fee'),
};
Say this in the interview

I use enums for any fixed set like order status, because an invalid value physically can't reach my logic and behaviour lives on the enum itself. readonly makes my DTOs and Money objects truly immutable. And match replaced my switches — it's strict, returns a value, and throws if nothing matches instead of silently doing nothing.

How a recruiter tests this

Asked as 'what's new in PHP 8?' or indirectly, by seeing whether you reach for enums when a status field appears in a live coding task. Reaching for string constants in 2026 reads as out of date.

Your drill

Model an order with an enum status, a readonly Money value object, and a match expression for fees. No AI. Then add a currency-mismatch test.

OOP, SOLID and design that survives questioning
30m
Picture it like this

Think of electrical sockets. Your wall socket doesn't care if you plug in a fan or a charger — it only cares about the plug shape (the interface). That's Open/Closed: new devices, zero rewiring. A value object like Money is like a sealed banknote — you never edit a 500 taka note into 600; you exchange it for different notes.

দেয়ালের সকেট জানে না ফ্যান লাগাবেন না চার্জার — শুধু প্লাগের আকৃতি (interface) মিললেই চলে। এটিই Open/Closed: নতুন যন্ত্র, কোনো নতুন ওয়্যারিং নয়। Money-র মতো value object সিল করা টাকার নোটের মতো — ৫০০-কে কেটে ৬০০ বানান না, বদলে নেন।

ধারণাটি সংক্ষেপে

SOLID মুখস্থ না বলে নিজের কাজের উদাহরণ দিয়ে বোঝান। যেমন Open/Closed মানে নতুন পেমেন্ট প্রোভাইডার যোগ করতে পুরনো কোড বদলাতে হবে না — শুধু নতুন ক্লাস, যা interface দিয়ে সম্ভব। মডেলিংয়ে তিনটি ধারণা গুরুত্বপূর্ণ: entity-র নিজস্ব পরিচয় থাকে যা টিকে থাকে; value object সম্পূর্ণভাবে তার মান দিয়ে নির্ধারিত হয় এবং immutable হওয়া উচিত (যেমন Money); DTO শুধু ডেটা বহন করে। Inheritance-এর চেয়ে composition ভালো, কারণ inheritance আপনাকে প্যারেন্ট ক্লাসের সাথে চিরতরে বেঁধে ফেলে। Trait ব্যবহার করুন সীমিতভাবে।

Nobody wants the acronym recited. They want to hear a decision you made using the underlying idea.

Single Responsibility — one reason to change. The practical test: can you describe the class without saying "and"? A ReportGenerator that also emails reports has two.

Open/Closed — extend without editing. In practice this means strategy interfaces: adding a new payment provider is a new class, not an edited switch.

Liskov — a subclass must work anywhere its parent does. The smell is an overridden method that throws "not supported".

Interface Segregation — many small interfaces beat one fat one; don't force implementers to stub methods.

Dependency Inversion — depend on abstractions. This is what DI containers exist to enable.

Beyond SOLID, three modelling ideas matter more than people expect. An entity has identity that persists — Customer #42 is the same customer after every field changes. A value object is defined entirely by its values and should be immutable: Money, DateRange, EmailAddress. A DTO carries data across a boundary and should be dumb.

Composition over inheritance because inheritance couples you to a parent's implementation permanently. PHP traits sit awkwardly between the two — convenient, but they hide dependencies and cause collision confusion, so keep them small and cross-cutting.

Patterns worth one sentence each: Strategy (swap an algorithm), Repository (abstract persistence), Factory (encapsulate construction), Observer (Laravel events), Decorator (wrap to add behaviour), Adapter (make a third-party SDK fit), Specification (a query rule as a composable object).

Example
<?php
// Open/Closed via Strategy — adding a provider never edits this file
interface PaymentProvider {
    public function charge(Money $amount, string $reference): PaymentResult;
}

final class Checkout {
    /** @param array<string, PaymentProvider> $providers */
    public function __construct(private array $providers) {}

    public function pay(string $providerKey, Money $amount, string $ref): PaymentResult {
        $provider = $this->providers[$providerKey]
            ?? throw new InvalidArgumentException("Unknown provider: {$providerKey}");
        return $provider->charge($amount, $ref);
    }
}

// Specification — composable query rules, testable in isolation
interface Specification { public function toQuery(Builder $q): Builder; }

final class ActiveCandidates implements Specification {
    public function toQuery(Builder $q): Builder { return $q->where('status', 'active'); }
}
final class ScoredAbove implements Specification {
    public function __construct(private int $min) {}
    public function toQuery(Builder $q): Builder { return $q->where('score', '>=', $this->min); }
}
Say this in the interview

For me SOLID is mostly one habit: depend on interfaces, not implementations. Adding Nagad payments was a new class behind a PaymentProvider interface — no existing code changed. I model Money and DateRange as immutable value objects, so a whole class of mutation bugs can't exist. And I prefer composition over inheritance because inheritance welds you to the parent forever.

How a recruiter tests this

Expect 'explain SOLID with an example from your work' and 'when would you NOT use the repository pattern?'. Dogmatic answers lose; reasoned trade-offs win.

Your drill

Take an old class with a switch that selects behaviour. Refactor to a strategy interface. Time-box 20 minutes.

The Laravel request lifecycle and service container
30m
Picture it like this

The lifecycle is airport security in reverse too: you pass check-in, security, gate (middleware, inward) — and on the way back your luggage passes through the same checkpoints outward. The container is a smart storeroom manager: you say 'I need a PaymentProvider' and it builds one, with everything it depends on, without you touching a wrench.

লাইফসাইকেল এয়ারপোর্টের মতো: চেক-ইন, সিকিউরিটি, গেট (মিডলওয়্যার) পেরিয়ে ঢোকেন — আর ফেরার পথে একই চেকপয়েন্ট দিয়ে বের হন; এটি পেঁয়াজের মতো, একমুখী পাইপ নয়। কনটেইনার হলো বুদ্ধিমান স্টোরকিপার: যা চাইবেন, তার সব যন্ত্রাংশসহ বানিয়ে হাতে দেবে।

ধারণাটি সংক্ষেপে

Laravel ইন্টারভিউয়ের সবচেয়ে সাধারণ প্রথম প্রশ্ন। ধারাবাহিকতা: index.php → অটোলোডার → Application (কনটেইনার) তৈরি → কার্নেল বুটস্ট্র্যাপ (সব প্রোভাইডারের register() তারপর boot()) → গ্লোবাল মিডলওয়্যার → রাউটার → রুট মিডলওয়্যার → কন্ট্রোলার → রেসপন্স আবার একই মিডলওয়্যার দিয়ে ফেরত → terminable মিডলওয়্যার। মূল কথা: মিডলওয়্যার একমুখী নয়, পেঁয়াজের মতো। কনটেইনার constructor-এর type-hint দেখে নির্ভরতা তৈরি করে। bind = প্রতিবার নতুন, singleton = অ্যাপে একটি, scoped = প্রতি রিকোয়েস্টে একটি (Octane-এ এই পার্থক্য গুরুত্বপূর্ণ, নইলে এক ইউজারের ডেটা অন্যের কাছে ফাঁস হতে পারে)।

This is the most common opening question for a senior Laravel role, because it separates people who use the framework from people who understand it.

The lifecycle: public/index.php receives the request → Composer autoloader → bootstrap/app.php creates the Application (which *is* the container) and binds the HTTP kernel → the kernel bootstraps environment, config, exception handling, then calls register() on every service provider, then boot() on every provider → global middleware → router matches → route and group middleware → the controller is resolved from the container with dependencies injected and route-model binding resolved → the response travels back outward through the same middleware → sent → terminable middleware runs after the response has left.

Say "the middleware is an onion, not a one-way pipeline" — that single sentence proves comprehension.

The container is an IoC container that constructs objects by reflecting on constructor type-hints. Bindings tell it how: bind (new each time), singleton (one per app lifecycle), scoped (one per request), instance (an existing object). Contextual binding gives different implementations to different consumers.

The scoped vs singleton distinction only matters under Octane/Swoole, where the app stays in memory between requests — and there a singleton holding request state leaks it across users. That is a genuine security bug and mentioning it marks you out.

Providers: register() only binds — never resolve there, because other providers may not be registered yet. boot() runs after all providers registered, so routes, policies, macros and listeners belong there.

Example
<?php
// AppServiceProvider
public function register(): void {
    // bind only — do NOT resolve services here
    $this->app->bind(PaymentProvider::class, BkashProvider::class);
    $this->app->singleton(RateLimiter::class);
    $this->app->scoped(TenantContext::class);   // one per request, Octane-safe
}

public function boot(): void {
    // safe to use other services now
    Model::preventLazyLoading(! app()->isProduction());
    Gate::policy(Order::class, OrderPolicy::class);
}

// Contextual binding: different disk per consumer
$this->app->when(ReportController::class)
          ->needs(Filesystem::class)
          ->give(fn() => Storage::disk('s3'));
Say this in the interview

Request hits index.php, the app — which IS the container — boots, every provider registers then boots, then the request passes inward through middleware to the router and controller, and the response travels back OUT through the same middleware — it's an onion, not a pipeline. bind gives a new instance each time, singleton one per app, scoped one per request — and under Octane that difference is a security issue, because a singleton holding request state leaks between users.

How a recruiter tests this

Almost guaranteed in a Laravel interview. Follow-ups: 'why can't you resolve in register()?', 'what does scoped solve?', 'are facades an anti-pattern?' (answer both sides).

Your drill

In a fresh app: define an interface, two implementations, bind one in a provider, inject into a controller, swap the binding and confirm behaviour changes without touching the controller.

Eloquent in depth — relations, N+1, transactions, locking
35m
Picture it like this

N+1 is sending a delivery boy to the market once per item on your list instead of once with the whole list — every trip is fast, but 200 trips take all day. And a transaction is NOT a queue ticket: two people can both see 'one seat left' and both pay. Only a lock (or the database refusing duplicates) makes the second person wait.

N+1 মানে বাজারে প্রতিটি আইটেমের জন্য আলাদা লোক পাঠানো — প্রতিটি ট্রিপ দ্রুত, কিন্তু ২০০ ট্রিপে সারাদিন। আর ট্রানজেকশন লাইনের টোকেন নয় — দুজনেই 'একটি সিট খালি' দেখে দুজনেই টাকা দিতে পারে; শুধু লক বা ডেটাবেজের unique constraint দ্বিতীয়জনকে থামায়।

ধারণাটি সংক্ষেপে

Eloquent নিয়ে সবচেয়ে বেশি প্রশ্ন হয়। N+1 সমস্যা: লুপের ভেতরে রিলেশন লোড করলে ১+N কোয়েরি চলে — ধরার সেরা উপায় preventLazyLoading(), যা ডেভেলপমেন্টে সাথে সাথে এরর দেয়। সমাধান with(), withCount(), বা প্রয়োজনে join। ট্রানজেকশনের ভেতরে queue job dispatch করলে commit-এর আগেই চলতে পারে, তাই afterCommit() ব্যবহার করুন। ডাবল বুকিং ঠেকাতে শুধু ট্রানজেকশন যথেষ্ট নয় — lockForUpdate(), ডেটাবেজে unique constraint, বা version কলাম লাগবে; এর মধ্যে ডেটাবেজ constraint সবচেয়ে নির্ভরযোগ্য কারণ ভবিষ্যতে কেউ ভুলে গেলেও এটি কাজ করে।

Expect more interview time here than anywhere else in Laravel.

N+1 is the most-asked Eloquent question. Looping over N parents, each lazily loading a relation, produces 1+N queries. Every query is fast; the page is slow. Detect it with Debugbar or Telescope, but the strongest answer is Model::preventLazyLoading() in development — it throws the moment it happens, so the bug cannot reach production. Fix with with(), load() after the fact, withCount() for counts, or constrained eager loads.

with() vs join() — with() runs a second query and hydrates models: no row duplication, clean object graph. join() is one flat query, required when you must filter or sort by a related column or aggregate across tables.

Transactions wrap multi-step writes atomically. Three gotchas that mark experience: a queued job dispatched inside a transaction can run before commit (use afterCommit()); nested transactions use savepoints, not real nesting; long transactions hold locks, so keep them short.

Concurrency is where booking and inventory systems break. A transaction gives atomicity, not exclusion — two requests can both read "available" before either writes. Fixes: lockForUpdate() (pessimistic, second request waits), a unique constraint (database refuses the duplicate), or a version column with retry (optimistic).

Model events do not fire on mass updates. Model::where(...)->update() bypasses observers entirely, so audit logs, cache invalidation and search indexing silently don't run.

Scopes — local scopes are reusable constraints; global scopes apply automatically, which is powerful for multi-tenancy and surprising for everyone who forgets them.

Example
<?php
// N+1 → 2 queries, and count without loading
$orders = Order::query()
    ->with(['customer:id,name'])
    ->withCount('items')
    ->where('status', OrderStatus::Paid)
    ->cursorPaginate(20);

// Preventing a double booking — the DB is the last line of defence
DB::transaction(function () use ($slotId, $userId) {
    $slot = Slot::where('id', $slotId)->lockForUpdate()->firstOrFail();

    if ($slot->booked_at !== null) {
        throw new SlotAlreadyBookedException();
    }

    $slot->update(['booked_at' => now(), 'user_id' => $userId]);

    // dispatch AFTER commit, or the worker may not see the row yet
    SendBookingConfirmation::dispatch($slot->id)->afterCommit();
});

// Schema-level guarantee that survives future developers:
// $table->unique(['resource_id', 'slot_start']);
Say this in the interview

N+1 means one query per row in a loop — I catch it with preventLazyLoading in development so it throws before it ships, and fix it with eager loading or withCount. For double bookings: a transaction alone doesn't help, because it gives atomicity, not exclusion. I use lockForUpdate so the second request waits, and a unique constraint on resource-plus-slot as the guarantee that survives future developers.

How a recruiter tests this

'Explain N+1 and three ways to fix it', 'how do you prevent double bookings?', 'what's the transaction + queue gotcha?'. These are pass/fail questions for senior backend.

Your drill

Build Customers/Orders/Products. Create an N+1 deliberately, enable preventLazyLoading, watch it throw, then fix it three ways and compare query counts.

Building APIs: resources, validation, pagination, versioning

API Resource হলো দোকানের শোকেস, টেবিল হলো গুদাম — গুদামে নতুন তাক (কলাম) যোগ করলেও শোকেসে ক্রেতা তা দেখে না। Offset পেজিনেশন মানে প্রতিবার লাইনের সামনে থেকে ২০,০০০ জন গোনা; cursor মানে 'টিকিট নম্বর ২০,০০০-এর পরেরটা থেকে' — সাথে সাথে।

ধারণাটি সংক্ষেপে

Form Request দিয়ে ভ্যালিডেশন ও অনুমোদন কন্ট্রোলার থেকে সরান। API Resource ডেটাবেজের গঠন আর API-র চুক্তিকে আলাদা রাখে — নতুন কলাম যোগ করলে সেটি ভুল করে বাইরে যায় না, আর whenLoaded() N+1 ঠেকায়। পেজিনেশনে paginate() মোট সংখ্যা গুনতে গিয়ে বড় টেবিলে ধীর হয়; cursorPaginate() দ্রুত কারণ এটি ইনডেক্স ব্যবহার করে। OFFSET ধীর হয় কারণ ডেটাবেজকে বাদ দেওয়া প্রতিটি সারি পড়তে হয়। স্ট্যাটাস কোডের অর্থ জানুন: ৪২২ ভ্যালিডেশন, ৪০১ লগইন নেই, ৪০৩ অনুমতি নেই, ৪০৯ কনফ্লিক্ট।

Form Requests move validation and authorization out of the controller. authorize() answers "may this user do this", rules() answers "is this input valid". API requests get a 422 with a structured body automatically. Use prepareForValidation() to normalise input first and custom Rule objects for reusable business rules.

API Resources are the boundary between your database shape and your public contract. Without them, adding a column leaks it and renaming one breaks clients. whenLoaded() also prevents your serializer from silently triggering N+1.

Pagination — paginate() runs a COUNT for total pages, which is expensive on large tables. simplePaginate() skips it. cursorPaginate() is keyset-based: stable under inserts and fast at any depth. Know *why* offset degrades — the database must read and discard every skipped row, so page 1000 reads 20,000 rows to return 20.

Status codes carry meaning: 201 with the resource on create, 204 on delete, 400 for malformed vs 422 for failed validation, 401 (not authenticated) vs 403 (not permitted), 409 for conflict, 429 for rate limited. Returning 404 instead of 403 for objects a user shouldn't know exist is a deliberate privacy choice.

Versioning — URI versioning is the pragmatic default. What matters in the answer is that you version because clients break, and you deprecate on a published timeline rather than silently.

Rate limiting per user and per IP, with tighter limits on login endpoints.

<?php
class StoreOrderRequest extends FormRequest {
    public function authorize(): bool {
        return $this->user()->can('create', Order::class);
    }
    public function rules(): array {
        return [
            'customer_id'        => ['required', 'integer', 'exists:customers,id'],
            'items'              => ['required', 'array', 'min:1'],
            'items.*.product_id' => ['required', 'integer', 'exists:products,id'],
            'items.*.qty'        => ['required', 'integer', 'min:1', 'max:999'],
        ];
    }
}

class OrderResource extends JsonResource {
    public function toArray($request): array {
        return [
            'id'          => $this->id,
            'status'      => $this->status->value,
            'total'       => (string) $this->total,          // never float over the wire
            'customer'    => new CustomerResource($this->whenLoaded('customer')),
            'items_count' => $this->whenCounted('items'),
            'created_at'  => $this->created_at->toIso8601String(),
        ];
    }
}
Say this in the interview

I always put a Resource between the table and the response, so the API contract is deliberate — adding a column never leaks it. Validation lives in Form Requests: authorize answers 'may they', rules answers 'is it valid', and Laravel returns a clean 422. For long lists I use cursorPaginate because offset makes the database read and throw away every skipped row.

'How do you stop your API leaking database columns?', 'paginate vs cursorPaginate — why?', '400 vs 422, 401 vs 403'. Sloppy status codes are a common downgrade signal.

Queues, jobs, events — and the two production truths
30m
Picture it like this

A queue worker is a kitchen cook who might faint after cooking a dish but before ringing the bell — so the order gets cooked again. If the dish is 'send 500 taka', cooking twice is a disaster; the fix is checking the ticket: 'already served? do nothing.' And workers memorize the recipe book at hiring time — change the book (deploy) without re-briefing them (queue:restart), and they cook from the old book.

Queue worker হলো এমন বাবুর্চি যে রান্না শেষ করে বেল বাজানোর আগেই অজ্ঞান হতে পারে — তাই একই অর্ডার আবার রান্না হয়। খাবারটি যদি 'টাকা পাঠানো' হয়, দুবার মানে বিপদ; সমাধান টিকিট চেক করা। আর বাবুর্চি রেসিপি মুখস্থ রাখে — বই বদলালে (ডিপ্লয়) নতুন করে না জানালে (queue:restart) পুরনো রেসিপিতেই রান্না চলে।

ধারণাটি সংক্ষেপে

ধীর বা ঝুঁকিপূর্ণ কাজ (ইমেইল, SMS, PDF, বাইরের API) কিউতে পাঠান। দুটি বাস্তব সত্য: (১) একটি জব দুবার চলতে পারে — worker কাজ শেষ করে acknowledge করার আগেই মরে যেতে পারে, তাই প্রতিটি জব idempotent বানাতে হবে; (২) worker আপনার কোড মেমরিতে ধরে রাখে, তাই প্রতিটি ডিপ্লয়ের পর queue:restart চালাতেই হবে, নইলে পুরনো কোড চলতে থাকবে। ইভেন্ট ব্যবহার করুন যখন এক ঘটনায় একাধিক প্রতিক্রিয়া লাগে; একটিমাত্র নির্দিষ্ট কাজের জন্য সরাসরি সার্ভিস কল করাই ভালো।

Anything slow or failure-prone belongs off the request cycle: email, SMS, PDFs, imports, third-party API calls, image processing, report generation.

Mechanics: a job is serialized to a driver (Redis, database, SQS); a worker process pulls and executes it. Key knobs: $tries, backoff() for exponential delay, $timeout, retryUntil(), a failed() hook plus the failed_jobs table, and ShouldBeUnique to prevent concurrent duplicates. Batches group jobs with progress and a completion callback; chains run them in sequence.

Truth one: jobs can run twice. A worker can die after doing the work but before acknowledging it. At-least-once delivery is what queue systems actually offer; exactly-once is marketing. So every job must be idempotent — check state before acting, key the operation on something stable, prefer setting a value over incrementing.

Truth two: workers hold your code in memory. After every deploy you must run queue:restart, or workers keep executing yesterday's code against today's database. Silently. For hours.

Events vs direct calls — events are for genuine fan-out where new reactions shouldn't modify the original code (OrderPlaced → email, stock, analytics). A direct service call is right when the step is required and singular. Overusing events makes control flow untraceable, and saying that shows judgement.

Scheduling — one cron entry runs schedule:run every minute. Use withoutOverlapping() and onOneServer() on multiple servers, and have scheduled tasks dispatch jobs rather than doing work inline.

Example
<?php
class SendCampaignEmail implements ShouldQueue {
    public int $tries = 3;
    public int $timeout = 30;

    public function __construct(public int $leadId, public int $campaignId) {}

    public function backoff(): array { return [10, 60, 300]; }

    public function handle(Mailer $mailer): void {
        // idempotent: a second run is a no-op, not a second email
        $already = Delivery::where('lead_id', $this->leadId)
            ->where('campaign_id', $this->campaignId)
            ->exists();
        if ($already) return;

        DB::transaction(function () use ($mailer) {
            Delivery::create([
                'lead_id' => $this->leadId,
                'campaign_id' => $this->campaignId,
                'sent_at' => now(),
            ]);
            $mailer->to(...)->send(...);
        });
    }

    public function failed(Throwable $e): void {
        Log::error('Campaign send failed', ['lead' => $this->leadId, 'e' => $e->getMessage()]);
    }
}
Say this in the interview

Two things I treat as law with queues. Every job can run twice — a worker can die after the work but before the acknowledgment — so every job checks state before acting and a repeat is a no-op. And workers hold code in memory, so queue:restart is part of every deploy; skip it and yesterday's code runs against today's database for hours.

How a recruiter tests this

'What happens if a job runs twice?' and 'what do you do after deploying when queues are running?' are direct experience tests. Missing the worker-restart answer suggests you have never run queues in production.

Your drill

Write a genuinely idempotent job. Run it twice manually and prove nothing duplicates. Then kill the worker mid-job and watch the retry.

Auth, authorization and multi-tenancy
30m
Picture it like this

A JWT is a laminated ID card: anyone can READ it (it's just base64), but nobody can FORGE it (the signature). The catch — you can't un-issue a laminated card, so keep expiry short. Multi-tenancy with tenant_id is one apartment building with one master corridor: forget to lock ONE door (one WHERE clause) and a stranger walks into someone's flat. Row-level security is giving the building itself the rule: 'this key only opens this flat.'

JWT হলো লেমিনেট করা আইডি কার্ড — যে কেউ পড়তে পারে (base64), কিন্তু জাল করতে পারে না (সিগনেচার)। সমস্যা: বিলি করা কার্ড ফেরত নেওয়া যায় না, তাই মেয়াদ ছোট রাখুন। tenant_id মানে এক বিল্ডিংয়ে সবাই — একটি দরজা লক করতে ভুললেই (একটি WHERE) অন্যের ফ্ল্যাটে ঢোকা যায়।

ধারণাটি সংক্ষেপে

Sanctum সাধারণত সঠিক পছন্দ — SPA-র জন্য কুকি, মোবাইলের জন্য টোকেন। Passport শুধু OAuth2 দরকার হলে। JWT স্টেটলেস কিন্তু বাতিল করা কঠিন, তাই স্বল্পমেয়াদী access token ও ঘূর্ণায়মান refresh token ব্যবহার করুন। মনে রাখবেন JWT-র payload এনক্রিপ্টেড নয়, শুধু সাইন করা — তাই গোপন তথ্য রাখবেন না। মাল্টি-টেন্যান্সির চারটি মডেল: tenant_id কলাম (সস্তা কিন্তু একটি ভুলে ডেটা ফাঁস), row-level security (ডেটাবেজেই সুরক্ষা), স্কিমা প্রতি টেন্যান্ট, ডেটাবেজ প্রতি টেন্যান্ট। সবচেয়ে বড় ঝুঁকি cross-tenant leakage — কোনো এরর দেয় না, তাই স্কোপিং ডিফল্ট হতে হবে।

Choosing a mechanism: Sanctum for first-party apps — cookie auth for a same-domain SPA, revocable API tokens with abilities for mobile. Passport only when third parties authorize against you via OAuth2. JWT when a token must be verified by multiple services without a central session store — accepting that revocation is the hard part, solved with short-lived access tokens plus rotating refresh tokens with reuse detection.

Never claim a JWT is encrypted. The payload is base64 and readable by anyone; it is signed, not secret. Verify the signature and check exp, iss, aud, and reject alg: none.

Gates vs Policies — gates are closures for one-off checks; policies are a class per model with methods matching actions, auto-discovered, invoked via authorize() in controllers or Form Requests.

Multi-tenancy — four models, and interviewers want the trade-offs rather than a favourite. Shared database with a tenant_id column is cheapest but one forgotten filter leaks data. Postgres row-level security moves enforcement into the database so an application bug still cannot leak. Schema per tenant gives better isolation with multiplying migrations. Database per tenant is strongest and heaviest.

The senior framing: cross-tenant leakage is the top risk, it produces no error and no alert, and therefore scoping must be the *default* rather than something you remember. An unscoped query should be the exception you write deliberately.

Example
<?php
// Global scope makes tenant filtering the default, not a thing you remember
class BelongsToTenant {
    public static function bootBelongsToTenant(): void {
        static::addGlobalScope('tenant', function (Builder $q) {
            if ($tenantId = app(TenantContext::class)->id()) {
                $q->where($q->getModel()->getTable().'.tenant_id', $tenantId);
            }
        });

        static::creating(function ($model) {
            $model->tenant_id ??= app(TenantContext::class)->id();
        });
    }
}

// Policy — authorize the object, not just the user
class OrderPolicy {
    public function view(User $user, Order $order): bool {
        return $user->tenant_id === $order->tenant_id
            && ($user->id === $order->user_id || $user->isAdmin());
    }
}
// Controller: $this->authorize('view', $order);
Say this in the interview

Sanctum is my default for first-party apps; JWT only when multiple services must verify without a central store, accepting that revocation is the hard part — short expiry, rotating refresh tokens. And a JWT is signed, not encrypted: anyone can read it. For multi-tenancy I make scoping the default with a global scope, because the worst bug — cross-tenant leakage — throws no error. An unscoped query has to be deliberate.

How a recruiter tests this

'How would you implement multi-tenancy?' and 'how do you guarantee no cross-tenant leakage?' are standard for SaaS roles. Also expect IDOR probing: 'what stops me changing the ID in the URL?'

Your drill

Add Sanctum plus a policy so users see only their own orders. Then try to fetch another user's order by ID and confirm you get 403 or 404, not data.

Caching, performance and diagnosing a slow application
25m
Picture it like this

Caching is keeping a photocopy of a document at your desk instead of walking to the archive room every time. The hard question is never the copy — it's knowing when the original changed. And diagnosing slowness is being a doctor: you don't prescribe surgery because the patient says 'I feel slow' — you run tests first. The X-ray here is Telescope and EXPLAIN.

ক্যাশিং মানে আর্কাইভ রুমে বারবার না গিয়ে ডেস্কে ফটোকপি রাখা — কঠিন প্রশ্ন কপিটা নয়, আসল কাগজ কখন বদলালো তা জানা। আর ধীর অ্যাপ সারানো ডাক্তারের কাজের মতো: 'ধীর লাগছে' শুনেই অপারেশন নয় — আগে টেস্ট (Telescope, EXPLAIN), পরে চিকিৎসা।

ধারণাটি সংক্ষেপে

ক্যাশিংয়ে সবচেয়ে কঠিন অংশ invalidation — কখন পুরনো ডেটা মুছবেন। সহজ সমাধান TTL, প্রয়োজনে ইভেন্ট-ভিত্তিক বা ভার্সনড কী। ধীর অ্যাপ ঠিক করার প্রশ্নে সবচেয়ে গুরুত্বপূর্ণ উত্তর: আগে মাপুন, অনুমান করবেন না। তারপর ক্রমানুসারে — N+1 ও অনুপস্থিত ইনডেক্স ঠিক করুন (বাস্তবে ৮০% সমস্যা এখানেই), তারপর ক্যাশ, তারপর ধীর কাজ কিউতে, তারপর config:cache ও OPcache, সবশেষে সার্ভার। শুরুতেই সার্ভার বাড়ানোর কথা বললে খারাপ ছাপ পড়ে। মনে রাখবেন config:cache করার পর config ফাইলের বাইরে env() কাজ করে না।

Patterns: Cache::remember($key, $ttl, $callback) is the read-through workhorse. Atomic locks (Cache::lock()) prevent two workers doing the same expensive job. Cache tags allow group invalidation on Redis and Memcached.

Invalidation is the hard part. TTL is simplest and correct whenever staleness is tolerable — which is most of the time. Event-based invalidation on model save is accurate but more code, and it misses mass updates. Versioned key prefixes invalidate a whole group at once.

Diagnosing slowness — the answer they want. Always measure first. Telescope, Debugbar, an APM, EXPLAIN, browser devtools tell you whether it is the database, PHP, an external call, or the frontend. Then fix in order: N+1 and missing indexes (genuinely 80% of real cases), cache expensive reads, move slow work to queues, then config:cache/route:cache/OPcache, and only then infrastructure.

Opening with "add more servers" is a downgrade signal. Opening with "I would measure first" is half the marks.

The config:cache trap: once configuration is cached, env() returns null outside config files. Call env() in a service class and it works in development and silently breaks in production. Always read through config().

Octane keeps the app in memory for real speed gains, at the cost that any state held in a singleton now leaks between requests.

Example
<?php
// Read-through cache with a versioned key for group invalidation
$version = Cache::get("tenant:{$tenantId}:dash:v", 1);

$stats = Cache::remember("tenant:{$tenantId}:dash:v{$version}", 300, function () use ($tenantId) {
    return [
        'revenue_today' => Order::whereDate('created_at', today())->sum('total'),
        'open_orders'   => Order::where('status', OrderStatus::Pending)->count(),
    ];
});

// Invalidate the whole group by bumping the version — no key enumeration
Cache::increment("tenant:{$tenantId}:dash:v");

// Atomic lock: stop two workers processing the same payout
Cache::lock("payout:{$payoutId}", 30)->get(function () use ($payoutId) {
    ProcessPayout::run($payoutId);
});
Say this in the interview

My rule on a slow endpoint: measure before touching anything — Telescope or an APM tells me if it's the database, PHP, or an external call. Eighty percent of the time it's N+1 or a missing index, so that's where I start; then caching with a sensible TTL, then moving slow work to queues, and infrastructure only last. And I never call env() outside config files — after config:cache it silently returns null in production.

How a recruiter tests this

'This endpoint is slow, walk me through what you do.' They are scoring your *order of operations*, not your knowledge of caching APIs.

Your drill

Cache one endpoint. Measure before and after with a real tool. Then break invalidation deliberately and observe stale data, so you understand the cost.

Symfony, Doctrine and testing

Picture it like this

Eloquent is a self-driving suitcase — tell it 'save yourself' and it rolls to storage. ধারণাটি সংক্ষেপে

JavaScript-এ সবচেয়ে বেশি জিজ্ঞাসিত প্রশ্ন। নিয়ম: প্রথমে সিনক্রোনাস কোড চলে, তারপর সব microtask (promise) শেষ হয়, তারপর macrotask (setTimeout)। তাই setTimeout 0 দিলেও promise আগে চলবে। Promise.all যেকোনো একটি ব্যর্থ হলেই থেমে যায়; allSettled সবগুলোর ফল দেয় — আংশিক সফলতা গ্রহণযোগ্য হলে এটি ব্যবহার করুন। মনে রাখবেন forEach-এর ভেতরে await কাজ করে না — for...of বা Promise.all ব্যবহার করুন। AbortController দিয়ে চলমান রিকোয়েস্ট বাতিল করা যায়, যা সার্চ বক্সে অপরিহার্য।

The single most-asked JavaScript question, and the one most candidates fumble.

Synchronous code runs on the call stack. When it finishes, microtasks drain completely — promise callbacks, await continuations, queueMicrotask. Only then does the next macrotask run: setTimeout, setInterval, I/O. Then microtasks drain again, and so on.

So a setTimeout(fn, 0) always runs *after* every pending promise callback, no matter how many there are. Be able to explain why, not just recite the order.

Promise combinators: Promise.all rejects as soon as any input rejects — use it when you need everything. allSettled waits for all and reports each outcome — correct when partial success is acceptable, like sending fifty emails. race settles with the first result. any resolves with the first fulfilment.

The forEach trap: items.forEach(async i => await save(i)) fires every call and awaits none, so the surrounding function continues immediately and errors vanish. Use for...of for sequential or Promise.all(items.map(...)) for parallel.

Cancellation: AbortController cancels in-flight requests. Essential for search-as-you-type, and the fix for the stale-response race where a slow earlier request resolves after a newer one and overwrites correct data.

Error handling: try/catch around await, and remember an unhandled rejection in a floating promise crashes Node by default.

Example
// Predict the output — a classic screening question
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
queueMicrotask(() => console.log('4'));
console.log('5');
// 1, 5, 3, 4, 2   — all microtasks drain before any timer

// The forEach trap
async function saveAllWrong(items) {
  items.forEach(async (i) => { await save(i); });   // returns immediately
  console.log('done');                              // lies
}
async function saveAllRight(items) {
  await Promise.all(items.map(i => save(i)));       // parallel
  // or: for (const i of items) await save(i);      // sequential
}

// Cancellation for search-as-you-type
let controller;
async function search(term) {
  controller?.abort();
  controller = new AbortController();
  try {
    const res = await fetch(`/api/search?q=${encodeURIComponent(term)}`,
                            { signal: controller.signal });
    return await res.json();
  } catch (e) {
    if (e.name !== 'AbortError') throw e;
  }
}
Say this in the interview

Sync code runs first, then ALL microtasks — promise callbacks and awaits — drain completely, and only then a macrotask like setTimeout runs, even at zero milliseconds. That ordering answers most output-prediction questions. Two traps I always flag: forEach doesn't await, so I use for...of or Promise.all; and every fetch in a search box gets an AbortController, or a slow old response overwrites the fresh one.

ধারণাটি সংক্ষেপে

Closure মানে ফাংশন তার তৈরি হওয়ার স্কোপ মনে রাখে — debounce, throttle, memoize সবই এর উপর দাঁড়িয়ে। `this` নির্ধারিত হয় কল করার জায়গা দেখে, সংজ্ঞা দেখে নয়: মেথড কলে ডটের আগের অবজেক্ট, সাধারণ কলে undefined, arrow function-এ বাইরের স্কোপ থেকে উত্তরাধিকারসূত্রে পাওয়া (পরিবর্তন করা যায় না)। ইন্টারভিউতে মুখস্থ লিখতে পারা দরকার: debounce, throttle, deep clone, flatten, memoize। debounce কল থামার পর একবার চলে (সার্চ বক্স), throttle নির্দিষ্ট সময় পরপর একবার চলে (scroll)।

Closures — a function retaining access to its defining scope after that scope returns. This is the mechanism behind private state, memoization, and every debounce or throttle implementation you will be asked to write.

this binding is determined by the call site, not the definition: a method call binds the object before the dot; a plain call is undefined in strict mode; an arrow function inherits this lexically and cannot be rebound; call/apply/bind set it explicitly; new binds the fresh instance. The classic bug is a callback losing this, and arrow functions are the fix.

Prototypes — objects delegate to a prototype chain, and class is sugar over it. Worth understanding for the "how does inheritance work in JS?" question.

Functions you should be able to write from memory in an interview: debounce, throttle, deep clone, flatten, memoize, a simple event emitter, and Promise.all from scratch. These are the most common live-coding warm-ups for senior frontend roles, and fumbling them is disproportionately damaging because they are considered basics.

Debounce fires once after calls *stop* — right for a search input. Throttle fires at most once per window *during* continuous calls — right for scroll and resize. Knowing which to reach for is as important as writing them.

Example
// Write these from memory — they appear constantly
function debounce(fn, wait) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), wait);
  };
}

function throttle(fn, limit) {
  let ready = true;
  return function (...args) {
    if (!ready) return;
    fn.apply(this, args);
    ready = false;
    setTimeout(() => { ready = true; }, limit);
  };
}

function memoize(fn) {
  const cache = new Map();
  return (...args) => {
    const key = JSON.stringify(args);
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key);
  };
}

function deepClone(value, seen = new WeakMap()) {
  if (value === null || typeof value !== 'object') return value;
  if (seen.has(value)) return seen.get(value);          // circular refs
  if (value instanceof Date) return new Date(value);
  const out = Array.isArray(value) ? [] : {};
  seen.set(value, out);
  for (const [k, v] of Object.entries(value)) out[k] = deepClone(v, seen);
  return out;
}
Say this in the interview

A closure is a function that keeps access to its birth scope — that's the mechanism behind debounce, throttle and memoize, all of which I can write from memory. Debounce fires once after calls stop, so it's for search inputs; throttle fires at most once per window during continuous events, so it's for scroll. And this is decided by the call site — arrow functions inherit it lexically, which is why they fix lost-this bugs in callbacks.

ধারণাটি সংক্ষেপে

TypeScript-এ সবচেয়ে গুরুত্বপূর্ণ পার্থক্য any আর unknown-এর মধ্যে। any টাইপ চেকিং বন্ধ করে দেয় এবং ধীরে ধীরে পুরো কোডবেসে ছড়ায়; unknown সব নেয় কিন্তু ব্যবহারের আগে টাইপ নিশ্চিত করতে বাধ্য করে — তাই API রেসপন্সের জন্য এটিই সঠিক। মনে রাখবেন `as` দিয়ে cast করা মানে কম্পাইলারকে মিথ্যা বলা, রানটাইমে কোনো সুরক্ষা নেই — zod দিয়ে যাচাই করুন। Discriminated union দিয়ে loading/success/error অবস্থা সুন্দরভাবে মডেল করা যায় এবং switch exhaustive কিনা কম্পাইলার ধরতে পারে।

unknown vs any is the distinction that matters most. any disables checking and spreads silently through the codebase. unknown accepts anything but forces narrowing before use, which makes it the correct type at every boundary — API responses, JSON.parse, third-party data.

Critically: a cast (data as User) is a lie the compiler believes. There is no runtime check. Validate at the boundary with a schema library instead.

Narrowing — typeof, instanceof, the in operator, type predicates (function isUser(x): x is User), and discriminated unions. A discriminated union with a status or kind field is the idiomatic way to model "one of several shapes", and it makes exhaustive switches checkable.

Generics when a function's output type depends on its input type; constrain with extends when you need guarantees.

Utility types worth knowing by name: Partial, Required, Pick, Omit, Record, ReturnType, Awaited, NonNullable.

Strict mode is the expectation now. Mention strictNullChecks specifically — it eliminates an entire category of runtime error.

The senior framing: types are not decoration, they are a design tool. If you find yourself writing a type that is awkward to express, that is usually a sign the data model is wrong rather than the type system being limited.

Example
// Discriminated union: the compiler enforces every case is handled
type Result<T> =
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'success'; data: T };

function render(r: Result<User>) {
  switch (r.status) {
    case 'loading': return spinner();
    case 'error':   return message(r.error);   // TS knows .error exists
    case 'success': return profile(r.data);    // TS knows .data exists
    default: {
      const _exhaustive: never = r;            // compile error if a case is added
      return _exhaustive;
    }
  }
}

// Boundary: validate, don't cast
import { z } from 'zod';
const UserSchema = z.object({ id: z.number(), email: z.string().email() });
type User = z.infer<typeof UserSchema>;

async function getUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  const data: unknown = await res.json();
  return UserSchema.parse(data);   // throws on mismatch — real safety
}
Say this in the interview

At every boundary — API responses, JSON.parse — I type the data as unknown and validate with zod before it enters the app, because a cast is a lie the compiler believes with zero runtime safety. Inside the app I model states as discriminated unions — loading, error, success — so the compiler proves I handled every case, and an added case becomes a compile error, not a production bug.

ধারণাটি সংক্ষেপে

ফ্রন্টএন্ড সিনিয়রিটি এখানেও যাচাই হয়। ৪০১ মানে আপনি কে জানি না, ৪০৩ মানে জানি কিন্তু অনুমতি নেই। CORS হলো ব্রাউজারের নিরাপত্তা ব্যবস্থা, সার্ভারের নয় — CORS এরর মানে আপনার API নিরাপদ, এমন নয়; যে কেউ curl দিয়ে কল করতে পারে। টোকেন localStorage-এ রাখবেন না, কারণ যেকোনো XSS সেটি পড়ে ফেলতে পারে; httpOnly কুকি JavaScript পড়তে পারে না। সাথে secure (শুধু HTTPS) এবং sameSite (CSRF ঠেকায়) ফ্ল্যাগ দিন। ক্যাশিং হেডার দিয়ে ব্যান্ডউইথ ও গতি দুটোই বাঁচে।

Frontend seniority is tested here as much as in framework knowledge.

Status codes carry meaning — 401 means "I don't know who you are", 403 means "I know and you may not". Mixing them up is a common tell.

CORS is a browser restriction, not a server security feature. The browser blocks a page on origin A from *reading* a response from origin B unless B permits it. It does not protect your API — anyone can call it with curl. So a CORS error never means your API is secure. For non-simple requests the browser sends a preflight OPTIONS first; if your API rejects OPTIONS, everything breaks. And Access-Control-Allow-Origin: * cannot be combined with credentials.

Storage and tokens. localStorage is readable by any JavaScript on the page, which means any XSS steals your token instantly. An httpOnly cookie cannot be read by JavaScript at all. Add secure (HTTPS only) and sameSite (Lax or Strict blocks the cross-site request that makes CSRF possible). This is why cookies beat localStorage for session tokens, and it is a question that separates people who have thought about security from people who followed a tutorial.

Caching headers — Cache-Control (max-age, no-store, private vs public), ETag with If-None-Match returning 304. Hashed asset files get max-age=31536000, immutable; a dashboard gets no-store.

Example
// Server: session cookie done correctly
res.cookie('session', token, {
  httpOnly: true,        // JS cannot read it — XSS cannot steal it
  secure: true,          // HTTPS only
  sameSite: 'lax',       // blocks the cross-site request CSRF needs
  maxAge: 60 * 60 * 1000,
  path: '/',
});

// CORS: explicit origin required when credentials are involved
app.use(cors({
  origin: 'https://app.example.com',   // '*' is invalid with credentials
  credentials: true,
}));

// Caching: hashed assets forever, API data never
// app.js?v=8f3a1c   →  Cache-Control: public, max-age=31536000, immutable
// /api/dashboard    →  Cache-Control: no-store

Tokens never go in localStorage, because any XSS reads it instantly; they go in an httpOnly, secure, sameSite cookie — JS can't read it, HTTPS-only, and sameSite blocks the ambient request CSRF depends on.

Even in a PHP-primary role, Node comes up because your CV lists it.

The runtime model — single-threaded event loop with a thread pool for I/O. CPU-bound work blocks everything, which is the defining constraint. Heavy computation belongs in a worker thread, a separate service, or a queue.

Modules — ESM vs CommonJS, and why the interop is painful.

Streams for large data — read, transform, write without loading everything into memory. The same idea as PHP generators.

Error handling — an unhandled promise rejection terminates the process by default; a thrown error inside a callback is not caught by an enclosing try/catch. Async errors need explicit handling, and Express needs an error middleware with four arguments.

Express/Fastify basics — middleware ordering, route handlers, and centralized error handling. If you know Laravel middleware, this is the same mental model.

Environment and config — never commit secrets, validate environment variables at startup so the process fails fast rather than at 3am.

What interviewers actually probe: whether you understand that Node's concurrency comes from non-blocking I/O rather than threads, and whether you know what happens when you block the loop.

Example
// Blocking the event loop — the classic Node mistake
app.get('/report', (req, res) => {
  const result = heavyCalculation(req.query);   // blocks EVERY request
  res.json(result);
});

// Correct: offload it
app.get('/report', async (req, res) => {
  const job = await queue.add('generate-report', { params: req.query });
  res.status(202).json({ jobId: job.id });      // 202 Accepted, poll later
});

// Streaming a large file instead of buffering it
app.get('/export', (req, res) => {
  res.setHeader('Content-Type', 'text/csv');
  db.query('SELECT * FROM orders').stream()
    .pipe(toCsv())
    .pipe(res)
    .on('error', (e) => { logger.error(e); res.destroy(e); });
});

// Fail fast on bad config, at boot, not at 3am
const required = ['DATABASE_URL', 'JWT_SECRET'];
for (const k of required) if (!process.env[k]) throw new Error(`Missing env: ${k}`);
Say this in the interview

Node's concurrency comes from non-blocking I/O on a single thread, not from threads — so it's excellent at many simultaneous connections and terrible at heavy computation in a request, because that blocks everyone. CPU-heavy work goes to a queue or worker thread; large data gets streamed instead of buffered. And async errors need explicit handling — an unhandled rejection can take the whole process down.

The React mental model — rendering, state, and why most effects are wrong

Picture it like this

Keys are name tags on furniture: use position numbers (index) and when the sofa moves, the painter puts the sofa's paint on the table. And useEffect for derived values is calling a plumber to pour tea: computing total from items needs no ceremony — just compute it.

React প্রতিবার ঘর নতুন করে আঁকে, কিন্তু চালাক রংমিস্ত্রি — পুরনো ও নতুন নকশা মিলিয়ে শুধু বদলানো দেয়ালটাই রং করে। Key হলো আসবাবের নেমট্যাগ: পজিশন নম্বর (index) দিলে সোফা সরলে সোফার রং টেবিলে পড়ে। আর derived মানের জন্য useEffect মানে চা ঢালতে মিস্ত্রি ডাকা — total তো এমনিই হিসাব করা যায়।

ধারণাটি সংক্ষেপে

React-এর মূল ধারণা: UI হলো state-এর একটি ফাংশন। state বদলালে কম্পোনেন্ট আবার রেন্ডার হয়, React পুরনো ও নতুন ট্রি তুলনা করে শুধু প্রয়োজনীয় DOM পরিবর্তন করে। দুটি গুরুত্বপূর্ণ বিষয়: (১) key হিসেবে array index ব্যবহার করবেন না — লিস্ট বদলালে React ভুল নোডের সাথে ভুল ডেটা মেলায়; (২) re-render মানেই DOM আপডেট নয়, তাই আগেভাগে memoization করা সাধারণত অপচয়। আধুনিক দৃষ্টিভঙ্গি: বেশিরভাগ useEffect আসলে দরকার নেই — derived মান render-এর সময় হিসাব করুন, ডেটা ফেচিং ফ্রেমওয়ার্ককে দিন। useEffect শুধু বাইরের সিস্টেমের সাথে সিঙ্ক করার জন্য।

React's model is simple and consistently misunderstood: UI is a function of state. A state change triggers a re-render of that component and its children; React reconciles the new tree against the old using keys, then commits the minimal DOM changes.

Two consequences interviewers probe. First, keys must be stable IDs, never array indexes for reorderable lists — when the list changes, indexes shift, React matches the wrong node to the wrong data, and you get stale content and lost input state. Second, re-render does not mean DOM update; React re-runs your function and diffs. That is why "unnecessary re-renders" are usually cheap and premature memoization is usually waste.

The modern view of useEffect is that most effects should not exist. An effect synchronizes with something *outside* React — a subscription, a timer, a non-React widget. It is not for derived values (compute those during render) and increasingly not for data fetching (the framework or a query library does it better). Every effect needs a correct dependency array and a cleanup function.

useState vs useReducer — reducer when transitions are complex, when several values move together, or when you want the transition logic testable outside the component.

useMemo/useCallback memoize expensive computations and stable identities. Measure before reaching for them; sprinkling them everywhere adds cost and hides the real problem.

useRef for a mutable value that must not trigger renders, and for DOM access.

Example
// WRONG — derived state in an effect (two renders, a stale window, no benefit)
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(items.reduce((a, i) => a + i.price, 0));
}, [items]);

// RIGHT — just compute it during render
const total = items.reduce((a, i) => a + i.price, 0);

// Effects ARE for outside systems — note the cleanup
useEffect(() => {
  const socket = new WebSocket(url);
  socket.onmessage = (e) => setMessages(m => [...m, JSON.parse(e.data)]);
  return () => socket.close();          // without this you leak on every re-render
}, [url]);

// useReducer when transitions are real logic
function cartReducer(state, action) {
  switch (action.type) {
    case 'add':    return { ...state, items: [...state.items, action.item] };
    case 'remove': return { ...state, items: state.items.filter(i => i.id !== action.id) };
    case 'clear':  return { ...state, items: [] };
    default: throw new Error(`Unknown action: ${action.type}`);
  }
}
Say this in the interview

UI is a function of state: state changes, React re-renders and diffs, only real changes hit the DOM. Keys must be stable IDs, never the index on reorderable lists, or React matches wrong nodes to wrong data. And my default position on useEffect is that most shouldn't exist — derived values are computed during render, data fetching belongs to the framework or a query library; effects are only for synchronizing with the outside world, always with cleanup.

'What does useEffect actually do?' and 'why is index a bad key?' are standard. A candidate who puts derived state in an effect during live coding is marked down immediately.

Your drill

Take a component with three useEffects. Remove every one that computes derived state or fetches data, and confirm behaviour is unchanged.

ধারণাটি সংক্ষেপে

সবচেয়ে বাস্তবসম্মত লাইভ কোডিং প্রশ্ন: সার্চ বক্সে দ্রুত টাইপ করলে ধীর পুরনো রিকোয়েস্ট পরে এসে নতুন সঠিক ফলাফল মুছে দেয়। সমাধান — AbortController দিয়ে বাতিল করা, cleanup-এ ignore ফ্ল্যাগ রাখা, এবং ইনপুট debounce করা। loading ও error অবস্থা ফিচারের অংশ, সাজসজ্জা নয় — শুধু happy path লিখলে জুনিয়র মনে হয়। পারফরম্যান্সে: inline object বা array prop হিসেবে দিলে memoization ভেঙে যায় কারণ প্রতিবার নতুন রেফারেন্স তৈরি হয়। Context শুধু ধীরে বদলানো ডেটার জন্য (theme, user) — দ্রুত বদলালে পুরো সাবট্রি re-render হয়।

The stale response race is the most common realistic live-coding task for frontend seniors. A user types quickly; request A is slow, request B is fast; B resolves first, then A resolves and overwrites correct results with stale ones. The fixes: AbortController to cancel on each new input, an ignore flag in the cleanup so a late response is discarded, and debouncing the input. A production answer mentions all three and notes that a query library handles it for you.

Loading and error states are part of the feature, not decoration. A component with only a happy path is a junior signal. Model the states explicitly — a discriminated union in TypeScript makes it impossible to render success without data.

Performance — React.memo on components that re-render with identical props; stable props (inline objects and arrays break memoization because they are new references every render); list virtualization for long lists; lazy and Suspense for code splitting; and avoiding context that changes frequently, because every consumer re-renders.

Context is for low-frequency shared state — theme, current user, locale. Using it for fast-changing state re-renders the whole subtree. Split contexts or memoize the value.

Forms — controlled inputs give you validation and derived UI at the cost of a render per keystroke; uncontrolled with refs is faster and clumsier. Libraries exist because forms have many fields and re-rendering all of them per keystroke is genuinely slow.

Example
// The race-condition-safe fetch — write this from memory
useEffect(() => {
  if (!query) return;
  const controller = new AbortController();
  let ignore = false;

  (async () => {
    setState({ status: 'loading' });
    try {
      const res = await fetch(`/api/search?q=${encodeURIComponent(query)}`,
                              { signal: controller.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const data = await res.json();
      if (!ignore) setState({ status: 'success', data });
    } catch (e) {
      if (e.name === 'AbortError') return;            // expected, not an error
      if (!ignore) setState({ status: 'error', error: e.message });
    }
  })();

  return () => { ignore = true; controller.abort(); };
}, [query]);

// Memoization only works if props are referentially stable
const filters = useMemo(() => ({ status, from, to }), [status, from, to]);
const onSelect = useCallback((id) => setSelected(id), []);
<ExpensiveList filters={filters} onSelect={onSelect} />

For search-as-you-type I always handle the race: a fast new response can be overwritten by a slow old one. So each new input aborts the previous fetch with AbortController, the cleanup sets an ignore flag so a late response is discarded, and the input is debounced. And loading and error states are part of the feature — a component with only a happy path isn't finished, so I model the three states as a discriminated union.

Caching semantics have shifted between Next versions. The honest and correct interview answer is that you check the caching behaviour for the version you are on — which beats confidently quoting stale rules.

Vue 3 reactivity and the Composition API
30m
Picture it like this

ref is a labelled jar: the value sits inside, you open it with .value, and Vue notices every time the lid moves. reactive is jelly — poke anywhere and it wobbles everywhere, but cut a piece out (destructure) and that piece stops wobbling. A composable is a recipe card: every kitchen (component) that follows it cooks its OWN dish — unlike a store, which is one shared pot everyone eats from.

ref হলো লেবেল লাগানো বয়াম — মান ভেতরে, .value দিয়ে খোলেন, ঢাকনা নড়লেই Vue টের পায়। reactive হলো জেলি — যেখানেই খোঁচা দিন কাঁপে, কিন্তু এক টুকরো কেটে নিলে (destructure) সেই টুকরো আর কাঁপে না। Composable হলো রেসিপি কার্ড: প্রতিটি রান্নাঘর (কম্পোনেন্ট) নিজের রান্না করে — আর store হলো সবার এক হাঁড়ি।

ধারণাটি সংক্ষেপে

Vue ৩ Proxy দিয়ে reactivity ট্র্যাক করে। ref যেকোনো মান ধরে (script-এ .value, template-এ স্বয়ংক্রিয়); reactive শুধু অবজেক্টের জন্য এবং destructure করলে reactivity হারায় — toRefs দিয়ে ঠিক করা যায়। সাধারণ নিয়ম: ref ব্যবহার করুন, এটি অনুমানযোগ্য। computed ক্যাশ হয়, নির্ভরতা বদলালেই কেবল আবার হিসাব করে। Composable হলো Vue-র custom hook — reactive state ও ফাংশন রিটার্ন করে এমন সাধারণ ফাংশন, যা একই লজিক বহু কম্পোনেন্টে পুনঃব্যবহার করতে দেয়। ইন্টারভিউতে প্রায়ই লাইভ composable লিখতে বলা হয়।

Vue 3 tracks dependencies with Proxies. ref() wraps any value including primitives — .value in script, auto-unwrapped in templates. reactive() proxies an object deeply but loses reactivity when destructured, which is the most common Vue 3 bug; toRefs fixes it. The practical rule: default to ref because it behaves predictably.

computed() is a cached derived value, not a function call — it only recalculates when a dependency changes. watch takes explicit sources and is lazy; watchEffect auto-tracks whatever it touches and runs immediately.

Composition vs Options API — Composition groups code by *feature* rather than by option type, which is why large components stay readable and why logic becomes extractable. <script setup> is the modern default and removes most of the boilerplate.

Composables are Vue's answer to custom hooks: a function using reactivity APIs that returns reactive state and methods. Writing one live is the most common Vue interview task, so practise it until it is automatic. The key insight to articulate: a composable is instantiated per consumer, so each component gets its own state — unlike a store, which is shared.

Lifecycle — onMounted, onUnmounted (clean up listeners, intervals, subscriptions here), onUpdated, plus onActivated/onDeactivated with <KeepAlive>.

Example
<script setup>
import { ref, computed, watch, onUnmounted } from 'vue';

// composable: one instance per consumer, unlike a store
export function useCustomers(pageSize = 20) {
  const items   = ref([]);
  const loading = ref(false);
  const error   = ref(null);
  const query   = ref('');

  const filtered = computed(() =>
    items.value.filter(c => c.name.toLowerCase().includes(query.value.toLowerCase()))
  );

  let controller;
  async function load(page = 1) {
    controller?.abort();
    controller = new AbortController();
    loading.value = true;
    error.value = null;
    try {
      const res = await fetch(`/api/customers?page=${page}&per=${pageSize}`,
                              { signal: controller.signal });
      items.value = (await res.json()).data;
    } catch (e) {
      if (e.name !== 'AbortError') error.value = e.message;
    } finally {
      loading.value = false;
    }
  }

  onUnmounted(() => controller?.abort());
  return { items, filtered, query, loading, error, load };
}
</script>
Say this in the interview

I default to ref because it's predictable; reactive loses reactivity when destructured, which is the most common Vue 3 bug, and toRefs is the escape hatch. computed is a cached derived value, recalculating only when a dependency changes. And my rule for composable vs store: a composable is logic each component instantiates with its own state, a Pinia store is state shared across the app — mixing those two up is how apps get messy.

কম্পোনেন্ট যোগাযোগ: props নিচে, emit উপরে; v-model কম্পোনেন্টে modelValue + update:modelValue দিয়ে; গভীর ট্রিতে provide/inject (কম ব্যবহার করুন, কারণ ডেটার প্রবাহ অস্পষ্ট হয়)। Scoped slot দিয়ে child তার ডেটা parent-এর টেমপ্লেটে ফেরত দিতে পারে — নমনীয় টেবিল/লিস্ট কম্পোনেন্ট বানানোর মূল কৌশল। Pinia স্টোর হলো শেয়ার্ড অ্যাপ্লিকেশন স্টেট; composable হলো পুনঃব্যবহারযোগ্য লজিক যা প্রতিটি কম্পোনেন্ট আলাদাভাবে পায়। Nuxt-এ মডিউল লেভেলে ref রাখলে সার্ভারে এক ইউজারের ডেটা অন্যের কাছে যেতে পারে — সেজন্য useState আছে।

Nitro server routes (server/api/*) let you write real backend endpoints inside Nuxt. useHead/useSeoMeta for SEO.

Relational modelling and normalization that holds up
30m
Picture it like this

Normalization means every fact lives at ONE address — change it once, it's changed everywhere. But a receipt is a photograph, not a live link: the shop prints the price you PAID, because tomorrow's price change must not rewrite yesterday's receipt. Copying the price onto the order isn't breaking the rules — it's telling the truth about a moment in time.

Normalization মানে প্রতিটি তথ্যের একটিই ঠিকানা — একবার বদলালে সব জায়গায় বদলায়। কিন্তু রসিদ হলো ফটোগ্রাফ, লাইভ লিংক নয়: দোকান সেই দামটাই ছাপে যা আপনি দিয়েছেন, কারণ কালকের দাম বদল গতকালের রসিদ বদলাতে পারবে না। অর্ডারে দাম কপি করা নিয়ম ভাঙা নয় — একটি মুহূর্তের সত্য সংরক্ষণ।

ধারণাটি সংক্ষেপে

ডেটা মডেলিং প্রায়ই যাচাই করা হয়, কারণ খারাপ স্কিমার ক্ষতি সবচেয়ে দীর্ঘস্থায়ী। 3NF-এর সহজ অর্থ: প্রতিটি তথ্য একটিমাত্র জায়গায় থাকবে। তবে একটি গুরুত্বপূর্ণ ব্যতিক্রম আছে — অর্ডারের লাইনে পণ্যের দাম রাখা denormalization নয়, বরং সঠিকতা: দাম পরে বদলাতে পারে কিন্তু পুরনো অর্ডার বদলানো যাবে না। একই যুক্তি ঠিকানা বা ট্যাক্স রেটের ক্ষেত্রেও। কী নির্বাচনে: auto-increment ছোট ও দ্রুত কিন্তু ব্যবসার পরিমাণ ফাঁস করে; UUIDv4 এলোমেলো তাই ইনডেক্সে সমস্যা করে; ULID বা UUIDv7 সময় অনুযায়ী সাজানো, তাই সাধারণত সেরা।

Data modelling is tested more than people expect, because a bad schema outlives every other mistake.

Normalization to 3NF, stated plainly: each fact lives in one place. 1NF — atomic values, no comma-separated lists in a column. 2NF — no partial dependency on part of a composite key. 3NF — no transitive dependency, so no column that depends on another non-key column.

Deliberate denormalization for read-heavy reporting or precomputed counters, accepting the write cost and the risk of drift.

The distinction interviewers probe: storing the product price on the order line is not denormalization, it is correctness. Prices change; historical orders must not. The same applies to an address on a shipped order, or a tax rate on an invoice. If a fact was true at a moment and must stay true, copy it.

Keys — auto-increment integers are compact and index-friendly but leak volume and collide across systems. UUIDv4 is random, which hurts B-tree locality and causes page splits on insert. ULID or UUIDv7 are time-sortable and fix that, which is why they are the usual answer for distributed or multi-tenant systems.

Relationships — one-to-many via a foreign key; many-to-many via a join table, and the moment that join carries its own data (quantity, price, joined_at) it is an entity in its own right, not a pivot.

Constraints are documentation the database enforces: NOT NULL, UNIQUE, CHECK, foreign keys with the right ON DELETE behaviour.

Example
-- Correctness, not denormalization: the price at time of order
CREATE TABLE order_items (
  id           BIGINT PRIMARY KEY,
  order_id     BIGINT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id   BIGINT NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
  quantity     INT    NOT NULL CHECK (quantity > 0),
  unit_price   BIGINT NOT NULL,          -- minor units, copied at purchase time
  currency     CHAR(3) NOT NULL,
  UNIQUE (order_id, product_id)
);

-- A join table that grew data is an entity, not a pivot
CREATE TABLE subscriptions (
  tenant_id   BIGINT NOT NULL REFERENCES tenants(id),
  app_id      BIGINT NOT NULL REFERENCES apps(id),
  plan        TEXT   NOT NULL,
  started_at  TIMESTAMPTZ NOT NULL,
  expires_at  TIMESTAMPTZ,
  PRIMARY KEY (tenant_id, app_id)
);

-- ON DELETE RESTRICT on products: you must not lose order history
-- because someone deleted a product.

But I always distinguish that from correctness copies: the price on an order line, the address on a shipped order, the tax rate on an invoice are snapshots of a moment, copied on purpose because history must not change. For keys in distributed or multi-tenant systems I use ULID or UUIDv7 — time-sortable, so the index doesn't fragment like random UUIDs.

Picture it like this

An index is a phone book. It's sorted by surname-then-firstname — so it's instant for 'Rahman', instant for 'Rahman, Zia', and USELESS for 'everyone named Zia' (that's leftmost prefix). ইনডেক্স হলো ফোনবুক — পদবি-তারপর-নাম ক্রমে সাজানো। তাই 'Rahman' খোঁজা তাৎক্ষণিক, 'Rahman, Zia'-ও তাৎক্ষণিক, কিন্তু 'সবার মধ্যে Zia নামধারী' খুঁজতে অকেজো (এটিই leftmost prefix)। কলামে ফাংশন লাগানো — YEAR(created_at) — মানে ফোনবুককে বলা 'ছন্দ মেলে এমন নাম দাও': সাজানো কাজে লাগে না, প্রতিটি পাতা পড়তে হয়।

ধারণাটি সংক্ষেপে

B-tree ইনডেক্স হলো সাজানো একটি গাছ, যা পুরো টেবিল না পড়ে দ্রুত খুঁজে দেয়। কিন্তু প্রতিটি ইনডেক্স লেখার গতি কমায় ও জায়গা নেয় — তাই যা দিয়ে ফিল্টার/জয়েন/সর্ট করেন কেবল তাতেই দিন। সবচেয়ে বেশি জিজ্ঞাসিত নিয়ম leftmost prefix: (a,b,c) ইনডেক্স শুধু a, বা a+b, বা a+b+c দিয়ে খুঁজলে কাজ করে — শুধু b দিয়ে নয়। ইনডেক্স কাজ করে না যখন কলামে ফাংশন লাগান, শুরুতে wildcard দেন, বা কলামের ভিন্নতা কম। EXPLAIN পড়ে দেখুন full scan বা filesort আছে কিনা, আর examined সারি returned সারির চেয়ে অনেক বেশি কিনা।

How a B-tree index works — a sorted tree turning a full scan into a logarithmic lookup. Every index speeds reads and slows writes, because each insert and update maintains every index, plus storage. That trade-off is the entire answer to "should I add an index?"

The leftmost prefix rule is the most-asked index question. An index on (tenant_id, status, created_at) serves queries filtering on tenant_id, or tenant_id + status, or all three — but not status alone. So column order is a design decision. Put the column you always filter on first, equality conditions before range conditions, because a range stops the index being usable for subsequent columns.

A covering index contains every column the query needs, so the database never touches the table — an index-only scan.

When an index does not help: low-cardinality columns like booleans; leading wildcards (LIKE '%term'); a function wrapped around the column (WHERE YEAR(created_at) = 2026 — use a range instead); implicit type casts; and very small tables.

Reading EXPLAIN — look for full table scans on large tables, Using filesort, Using temporary, and rows examined vastly exceeding rows returned. In Postgres, a Seq Scan where you expected an Index Scan. EXPLAIN ANALYZE gives real timings rather than estimates.

Pagination at depth — OFFSET degrades because the database reads and discards every skipped row. Keyset pagination filters on the last seen value and uses the index directly.

Example
-- Query the index must serve
SELECT id, total FROM orders
WHERE tenant_id = 5 AND status = 'paid' AND created_at >= '2026-01-01'
ORDER BY created_at DESC
LIMIT 20;

-- Column order matters: equality first, range last
CREATE INDEX idx_orders_tenant_status_created
  ON orders (tenant_id, status, created_at DESC);

-- Covering index: never touches the table at all
CREATE INDEX idx_orders_covering
  ON orders (tenant_id, status, created_at DESC) INCLUDE (total);

-- Index-killers
WHERE YEAR(created_at) = 2026                        -- function on column: no index
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01'                     -- range: uses the index

-- Deep pagination: OFFSET reads and throws away 20,000 rows
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 20000;   -- slow
SELECT * FROM orders WHERE id > 20000 ORDER BY id LIMIT 20; -- keyset, fast
Say this in the interview

A composite index works like a phone book: leftmost columns first, so an index on tenant, status, date serves those combinations left to right — but never status alone. I put equality columns before range columns, and I never wrap an indexed column in a function, because that forces a full scan — a date range replaces YEAR(). Then I trust EXPLAIN over intuition: full scan, filesort, and rows-examined far above rows-returned are the three red flags.

How a recruiter tests this

'This query is slow — walk me through what you do' is standard for senior backend. They score your method: reproduce, EXPLAIN, check index and column order, then fix.

Your drill

Create a table with 100k rows. Run a query with no index, read EXPLAIN, add the composite index, re-run, and compare. Repeat until plan output feels familiar.

Transactions, isolation, locking and concurrency
30m
Picture it like this

A transaction is a money transfer between two pockets: either both movements happen or neither. But it is NOT a door lock — two people can walk through the same doorway mid-transfer. FOR UPDATE puts a 'wait here' sign on the row; the unique constraint is a doorman who physically cannot admit a second person; the version column is entering freely but your payment bouncing if someone got there first.

ট্রানজেকশন হলো দুই পকেটের মধ্যে টাকা সরানো — হয় দুটোই হবে নয়তো কিছুই না। কিন্তু এটি দরজার তালা নয় — মাঝপথে দুজনেই ঢুকে যেতে পারে। FOR UPDATE সারিতে 'এখানে অপেক্ষা করুন' সাইন; unique constraint এমন দারোয়ান যে দ্বিতীয়জনকে ঢুকতেই দেয় না; version কলাম মানে ঢুকতে পারবেন কিন্তু কেউ আগে পৌঁছে গেলে পেমেন্ট ফেরত।

ধারণাটি সংক্ষেপে

ACID: Atomicity (সব বা কিছুই না), Consistency, Isolation, Durability। Isolation level: Read Committed (PostgreSQL ডিফল্ট) নোংরা পড়া ঠেকায়; Repeatable Read (MySQL ডিফল্ট) একই সারি বারবার পড়লে একই ফল দেয়; Serializable সব ঠেকায় কিন্তু ধীর। ইন্টারভিউয়ের সবচেয়ে গুরুত্বপূর্ণ ধারণা: ট্রানজেকশন atomicity দেয়, exclusion নয় — দুটি ট্রানজেকশন একসাথে "খালি আছে" পড়ে দুজনই লিখতে পারে। তাই বুকিং বা স্টকে হয় FOR UPDATE দিয়ে লক করতে হবে, নয়তো ডেটাবেজে unique constraint দিতে হবে। Deadlock স্বাভাবিক ঘটনা — সব জায়গায় একই ক্রমে লক নিন এবং retry করুন।

ACID — Atomicity (all steps or none), Consistency (constraints hold), Isolation (concurrent transactions do not corrupt each other), Durability (committed survives a crash).

Isolation levels and the anomalies each prevents. Read Uncommitted allows dirty reads and is effectively never used. Read Committed (Postgres default) prevents dirty reads; non-repeatable reads remain possible. Repeatable Read (MySQL/InnoDB default) keeps row reads consistent within the transaction; phantoms are theoretically possible, though InnoDB blocks most with gap locks. Serializable prevents everything at real concurrency cost.

Define the anomalies in one line each: a dirty read is reading uncommitted data; a non-repeatable read is the same row differing when read again; a phantom is the same query returning new rows.

The critical insight for interviews: a transaction gives atomicity, not exclusion. Two transactions can both read "available" and both write. This is why booking and inventory systems need explicit locking or constraints.

Pessimistic (SELECT ... FOR UPDATE) makes the second transaction wait — right for short, high-contention operations. Optimistic (a version column, retry on conflict) avoids blocking — right for low-contention edits where waiting costs more than retrying.

Deadlocks occur when two transactions each hold what the other needs. Prevent by acquiring locks in a consistent order everywhere, keeping transactions short, and touching fewer rows. Then retry on deadlock, because deadlocks are a normal operating condition rather than a bug to eliminate.

Example
-- Pessimistic: the second transaction waits at the lock
BEGIN;
SELECT stock FROM products WHERE id = 10 FOR UPDATE;
-- another transaction reaching this line now blocks until we commit
UPDATE products SET stock = stock - 1 WHERE id = 10 AND stock > 0;
COMMIT;

-- Optimistic: no lock, detect the conflict on write
UPDATE bookings
   SET slot_start = '10:00', version = version + 1
 WHERE id = 5 AND version = 3;
-- 0 rows affected  →  someone else changed it  →  reload and retry

-- The guarantee that survives forgetful developers
ALTER TABLE bookings
  ADD CONSTRAINT uniq_resource_slot UNIQUE (resource_id, slot_start);

-- Deadlock avoidance: always lock in the same order everywhere
-- e.g. always lower id first
SELECT * FROM accounts WHERE id IN (:a, :b) ORDER BY id FOR UPDATE;
Say this in the interview

A transaction gives atomicity, not exclusion — that's the sentence that resolves most concurrency confusion. For contested writes I use SELECT FOR UPDATE so the second transaction waits, or a unique constraint so the database itself refuses the duplicate — the guarantee no future developer can forget. Deadlocks I treat as normal weather: consistent lock ordering to minimize them, short transactions, and retry when they happen anyway.

How a recruiter tests this

'How do you prevent a double booking?' is the single most common database concurrency question, and 'a transaction' is the wrong answer. Expect a follow-up on isolation levels.

Your drill

Open two DB sessions. Reproduce a lost update. Fix it with FOR UPDATE. Then deliberately cause a deadlock by locking two rows in opposite order.

Picture it like this

ROW_NUMBER OVER PARTITION BY is running a separate race per category and giving each runner their rank within their own race — 'top 3 per group' falls out instantly. And filtering a LEFT JOIN's right side in WHERE is inviting everyone to a party 'even without a gift', then turning away everyone giftless at the door — you silently made it an INNER JOIN. ROW_NUMBER OVER PARTITION BY মানে প্রতি ক্যাটেগরিতে আলাদা দৌড় — প্রত্যেকে নিজের দৌড়ে র‍্যাংক পায়, তাই 'প্রতি গ্রুপে সেরা ৩' সহজেই আসে। আর LEFT JOIN-এর ডান টেবিল WHERE-এ ফিল্টার করা মানে 'উপহার ছাড়াও আসুন' বলে দাওয়াত দিয়ে দরজায় উপহারহীনদের ফিরিয়ে দেওয়া — চুপচাপ INNER JOIN বানিয়ে ফেললেন; শর্তটি দাওয়াতপত্রে (ON) থাকা উচিত।

ধারণাটি সংক্ষেপে

ইন্টারভিউয়ে SQL লিখতে বলা হয়, বর্ণনা করতে নয়। LEFT JOIN-এর ডান পাশের টেবিলে WHERE দিয়ে ফিল্টার করলে সেটি চুপচাপ INNER JOIN হয়ে যায় — শর্তটি ON-এ দিতে হবে। WHERE গ্রুপ করার আগে সারি ফিল্টার করে, HAVING গ্রুপ করার পরে। Window function দিয়ে তিনটি কোয়েরির কাজ একটিতে হয়: ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) দিয়ে প্রতিটি গ্রুপের শীর্ষ N, SUM() OVER দিয়ে running total, LAG() দিয়ে আগের সারির সাথে তুলনা। মনে রাখবেন NULL কোনো মান নয় — NULL = NULL সত্য নয়, আর aggregate ফাংশন NULL বাদ দেয়।

Interviewers ask you to *write* SQL, not describe it. These are the shapes that cover most questions.

Joins — INNER returns matches only; LEFT returns all left rows with nulls where no match; FULL OUTER returns both sides. Be able to draw the result set. The classic trap is filtering a LEFT JOIN's right table in the WHERE clause, which silently turns it into an INNER JOIN — the condition belongs in the ON clause.

GROUP BY and HAVING — WHERE filters rows before grouping; HAVING filters groups after. Every non-aggregated column in the SELECT must appear in the GROUP BY.

Window functions turn three-query problems into one. ROW_NUMBER() OVER (PARTITION BY x ORDER BY y) answers the whole "top N per group" family. SUM() OVER (ORDER BY ...) gives running totals. LAG() and LEAD() compare a row to its neighbours, which is how you calculate month-over-month growth.

Subqueries vs joins vs CTEs — CTEs (WITH) make complex queries readable and are usually the right choice for multi-step logic. EXISTS is often faster than IN on large sets and handles NULLs more predictably.

COALESCE and NULL handling — NULL is not a value, it is the absence of one, so NULL = NULL is not true. Aggregates skip NULLs, which is why a LEFT JOIN with COUNT can surprise you: COUNT(*) counts rows including non-matches, COUNT(column) does not.

Example
-- Top 3 per category — memorize this shape
SELECT * FROM (
  SELECT p.*, ROW_NUMBER() OVER (PARTITION BY category_id ORDER BY sales DESC) AS rn
  FROM products p
) t WHERE rn <= 3;

-- Running total and month-over-month growth
WITH monthly AS (
  SELECT date_trunc('month', created_at) AS m, SUM(total) AS revenue
  FROM orders GROUP BY 1
)
SELECT m, revenue,
       SUM(revenue) OVER (ORDER BY m) AS running_total,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY m))
             / NULLIF(LAG(revenue) OVER (ORDER BY m), 0), 1) AS growth_pct
FROM monthly ORDER BY m;

-- Customers with no orders in 90 days (EXISTS beats NOT IN with NULLs)
SELECT c.* FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id AND o.created_at >= now() - interval '90 days'
);

-- The LEFT JOIN trap: this WHERE turns it into an INNER JOIN
SELECT c.*, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'paid';        -- WRONG: put it in the ON clause instead
Say this in the interview

The shapes I can write cold: ROW_NUMBER over a partition for top-N per group, SUM over an ordered window for running totals, LAG for month-over-month growth, and NOT EXISTS for 'customers with no recent orders' — safer than NOT IN because of NULLs. And I watch for the LEFT JOIN trap: filtering the right table in WHERE silently makes it an INNER JOIN; the condition belongs in ON.

How a recruiter tests this

Live SQL is common for backend roles. Expect top-N-per-group, a running total, and a 'find records with no matching child' query. Struggling with window functions is a senior-level gap.

Your drill

Write all four queries above from memory against a real database. Then write five more: duplicates, first-order cohort, monthly retention, top customer per month, and a keyset-paginated list.

Picture it like this

Big-O is asking 'if the guest list doubles, how much longer does the party prep take?' A hash map is a cloakroom with numbered tickets — coat number 512 is one step, whether there are ten coats or ten thousand. Big-O মানে জিজ্ঞেস করা: অতিথি দ্বিগুণ হলে আয়োজনে কতটা বেশি সময় লাগবে? হ্যাশ ম্যাপ হলো নম্বরওয়ালা টোকেনের ক্লোকরুম — ৫১২ নম্বর কোট আনা এক ধাপ, কোট দশটা হোক বা দশ হাজার। নেস্টেড লুপ মানে প্রতিটি অতিথির শার্ট প্রতিটি অতিথির সাথে মেলানো — ১০০ জনে ১০,০০০ তুলনা।

ধারণাটি সংক্ষেপে

সিনিয়র ফুলস্ট্যাক ইন্টারভিউতে খুব কঠিন অ্যালগরিদম সাধারণত আসে না, কিন্তু খরচ নিয়ে যুক্তি দিতে পারা লাগে। Big-O মানে ইনপুট বড় হলে সময় বা মেমরি কীভাবে বাড়ে: হ্যাশ ম্যাপে O(1), সর্টেড ডেটায় বাইনারি সার্চ O(log n), এক পাসে O(n), সর্টিং O(n log n), নেস্টেড লুপ O(n²)। স্পেস কমপ্লেক্সিটিও বলুন — অনেকে ভুলে যায়। সবচেয়ে বেশি দরকার হ্যাশ ম্যাপ, কারণ বেশিরভাগ প্রশ্নের সমাধান হলো নেস্টেড লুপকে হ্যাশ ম্যাপ দিয়ে O(n)-এ নামানো। বড় সুবিধা পাবেন যদি বলেন: ডেটা ডেটাবেজে থাকলে আমি এটি SQL-এ GROUP BY দিয়ে করতাম।

Senior full-stack interviews rarely go beyond medium difficulty. What they do test is whether you can reason about cost.

Big-O describes how time or memory grows as input grows — not actual speed. The ones you need: O(1) hash lookup, O(log n) binary search on sorted data, O(n) single pass, O(n log n) sorting, O(n²) nested loops. If you can say "this is O(n²) because of the nested loop, and a hash map makes it O(n)", you have answered most complexity questions at your level.

Space complexity matters too, and candidates forget it. A solution that builds a second copy of the input is O(n) space; an in-place one is O(1).

The structures that come up: hash map (O(1) average lookup — the answer to most interview problems), array (O(1) index, O(n) search), set (deduplication and membership), stack (LIFO — bracket matching, undo, DFS), queue (FIFO — job processing, BFS), tree (hierarchies, and the structure behind database indexes), graph (relationships, dependencies).

The senior move that scores disproportionately: when given a data-shaped problem, say what you would actually do in production. "In an interview I would write this with a hash map, but if this data lives in the database I would do it in SQL with a GROUP BY, because moving 100,000 rows into application memory to aggregate them is the real performance bug." That answer beats a clever algorithm.

Example
// Nested loop → hash map: the single most useful transformation
// O(n²)
function twoSumSlow(nums, target) {
  for (let i = 0; i < nums.length; i++)
    for (let j = i + 1; j < nums.length; j++)
      if (nums[i] + nums[j] === target) return [i, j];
  return [];
}

// O(n) time, O(n) space
function twoSum(nums, target) {
  const seen = new Map();
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i);
  }
  return [];
}

// The production answer, said aloud:
// "If these were order rows in Postgres I'd write
//  SELECT customer_id, SUM(total) FROM orders GROUP BY customer_id
//  rather than pulling them into memory."
Say this in the interview

I state complexity as growth: hash lookups O(1), binary search O(log n), a pass O(n), sorting O(n log n), nested loops O(n squared) — and the most useful transformation in interviews is replacing a nested loop with a hash map. I state space too, since in-place versus a copy matters. And when data lives in a database I say so: I'd aggregate with GROUP BY in SQL rather than hauling a hundred thousand rows into memory.

How a recruiter tests this

Complexity is asked as a follow-up to every coding task: 'what's the time complexity?' Not knowing it undoes an otherwise correct solution.

Your drill

For each problem you solve, state time AND space complexity aloud before checking. Do this for twenty problems.

শত শত প্রশ্ন মুখস্থ করার দরকার নেই — বেশিরভাগই পাঁচটি প্যাটার্নে পড়ে। এক: হ্যাশ ম্যাপ (জোড়া খোঁজা, ডুপ্লিকেট, গণনা)। দুই: টু-পয়েন্টার (সর্টেড অ্যারে, প্যালিনড্রোম)। তিন: স্লাইডিং উইন্ডো (সবচেয়ে লম্বা/ছোট সাবস্ট্রিং বা সাবঅ্যারে)। চার: সর্ট করে তারপর স্ক্যান (ইন্টারভাল মার্জ, শিডিউলিং — এটি আসলে বুকিং কনফ্লিক্ট সমস্যারই রূপ)। পাঁচ: রিকার্শন বা স্ট্যাক (নেস্টেড স্ট্রাকচার, ট্রি)। ইন্টারভিউতে কোড লেখার আগে জোরে বলুন কোন প্যাটার্ন — এটি বলাতেই বেশিরভাগ নম্বর আসে।

You do not need hundreds of problems. Almost everything at your level reduces to five patterns; learn to recognise which applies and the solution follows.

1. Hash map lookup. Signals: "find a pair", "have I seen this", "count occurrences". Turns O(n²) into O(n). Covers two-sum, duplicates, anagram grouping, first non-repeating character, frequency counts.

2. Two pointers. Signals: a sorted array, palindromes, "pair summing to X", removing duplicates in place. One pointer from each end, or fast/slow pointers for cycle detection.

3. Sliding window. Signals: "longest or shortest substring/subarray with property X". Expand the right edge, shrink the left when the constraint breaks. Covers longest substring without repeats, max sum of size k, minimum window.

4. Sort then scan. Signals: intervals, scheduling, "merge overlapping", "minimum rooms". Sorting first usually makes the rest linear. This is the booking-conflict problem in disguise — mention that connection, it converts an abstract exercise into real experience.

5. Recursion or an explicit stack. Signals: nested structures, trees, flatten, deep clone, directory traversal. Define the base case first, then the recursive step.

In the interview, say the pattern out loud before coding: "this looks like a sliding window because we need the longest substring satisfying a constraint." That sentence often earns most of the marks, because it demonstrates recognition rather than memorization.

Example
// Sliding window — learn this skeleton, it fits a whole family
function longestUnique(s) {
  const lastSeen = new Map();
  let start = 0, best = 0;
  for (let end = 0; end < s.length; end++) {
    const ch = s[end];
    if (lastSeen.has(ch) && lastSeen.get(ch) >= start) {
      start = lastSeen.get(ch) + 1;          // shrink past the duplicate
    }
    lastSeen.set(ch, end);
    best = Math.max(best, end - start + 1);
  }
  return best;
}

// Sort then scan — this IS the booking overlap problem
function mergeIntervals(intervals) {
  intervals.sort((a, b) => a[0] - b[0]);
  const out = [];
  for (const iv of intervals) {
    const last = out[out.length - 1];
    if (last && iv[0] <= last[1]) last[1] = Math.max(last[1], iv[1]);
    else out.push([...iv]);
  }
  return out;
}

// Two pointers
function isPalindrome(s) {
  let i = 0, j = s.length - 1;
  while (i < j) { if (s[i] !== s[j]) return false; i++; j--; }
  return true;
}

Before writing a line I name the pattern out loud: 'this reads like a sliding window, because we want the longest run satisfying a constraint' — that sentence alone earns marks, because it shows recognition, not memorization. Hash map for pairs and counts, two pointers for sorted data, sliding window for substrings, sort-then-scan for intervals — which is the booking-overlap problem I've solved in production — and recursion with a defined base case for anything nested.

ধারণাটি সংক্ষেপে

ফুলস্ট্যাক ইন্টারভিউতে ট্রি ও গ্রাফ কম আসে, কিন্তু একেবারে না পারলে খারাপ প্রভাব পড়ে। ট্রি traversal: in-order (BST-তে সাজানো ফল দেয়), pre-order (ট্রি কপি), post-order (ট্রি মুছে ফেলা বা আকার হিসাব)। DFS রিকার্শন বা স্ট্যাক দিয়ে, BFS কিউ দিয়ে স্তরে স্তরে। গ্রাফ সাধারণত adjacency list দিয়ে রাখা হয়। BFS দিয়ে সবচেয়ে ছোট পথ (ওজনহীন গ্রাফে), DFS দিয়ে গভীরে যাওয়া, আর cycle detection দিয়ে চক্রাকার নির্ভরতা ধরা। বাস্তব প্রয়োগ: ক্যাটেগরি হায়ারার্কি, নেস্টেড কমেন্ট, পারমিশন ইনহেরিটেন্স।

These appear less often in full-stack interviews than in FAANG-style ones, but "less often" is not never, and a blank here is costly.

Trees — binary tree traversals: in-order (left, node, right — gives sorted output on a BST), pre-order (node first — copying a tree), post-order (children first — deleting a tree, computing sizes). Depth-first uses recursion or a stack; breadth-first uses a queue and visits level by level.

Real-world tree problems in your domain: category hierarchies, organisational charts, nested comments, file systems, and the adjacency-list vs nested-set trade-off when storing them in SQL.

Graphs — represented as an adjacency list (a map of node to neighbours) far more often than a matrix. BFS finds the shortest path in an unweighted graph and uses a queue. DFS explores deeply and uses recursion or a stack. Cycle detection matters for dependency resolution — which is what a package manager or a job-ordering system does.

Recursion discipline: define the base case first, then the recursive step, and confirm the input shrinks toward the base case every time. If depth is a risk, convert to an explicit stack.

The realistic full-stack application of all this: nested category trees, permission inheritance, and "does this configuration have a circular dependency" — worth naming, because it grounds an abstract answer in real work.

Example
// BFS on a graph — shortest path, unweighted
function shortestPath(graph, start, goal) {
  const queue = [[start]];
  const visited = new Set([start]);
  while (queue.length) {
    const path = queue.shift();
    const node = path[path.length - 1];
    if (node === goal) return path;
    for (const next of graph.get(node) ?? []) {
      if (visited.has(next)) continue;
      visited.add(next);
      queue.push([...path, next]);
    }
  }
  return null;
}

// Cycle detection — "does this config depend on itself?"
function hasCycle(graph) {
  const WHITE = 0, GREY = 1, BLACK = 2;
  const colour = new Map([...graph.keys()].map(k => [k, WHITE]));
  const visit = (n) => {
    colour.set(n, GREY);
    for (const next of graph.get(n) ?? []) {
      if (colour.get(next) === GREY) return true;      // back edge = cycle
      if (colour.get(next) === WHITE && visit(next)) return true;
    }
    colour.set(n, BLACK);
    return false;
  };
  return [...graph.keys()].some(n => colour.get(n) === WHITE && visit(n));
}

// Flatten a category tree — the realistic version
function flatten(nodes, depth = 0, out = []) {
  for (const n of nodes) {
    out.push({ id: n.id, name: n.name, depth });
    if (n.children?.length) flatten(n.children, depth + 1, out);
  }
  return out;
}
Say this in the interview

DFS goes deep with recursion or a stack; BFS goes level by level with a queue and finds shortest paths in unweighted graphs. In real work these show up as category trees, nested comments, permission inheritance and circular-dependency checks — so when asked, I ground it there: flattening a category tree with depth, building a breadcrumb, or three-colour cycle detection for 'does this configuration depend on itself'. My recursion discipline: base case first, and prove the input shrinks toward it.

Picture it like this

Under load, systems fail like a restaurant on Eid: the kitchen (database) chokes first, not the dining room (app servers) — so hiring more waiters fixes nothing. The thundering herd is the moment the ONE popular dish runs out and forty waiters storm the kitchen for it at once — the fix is one waiter cooks while the rest tell customers 'two minutes' (a lock, serve stale).

চাপে সিস্টেম ভাঙে ঈদের দিনের রেস্টুরেন্টের মতো: আগে রান্নাঘর (ডেটাবেজ) আটকায়, ডাইনিং রুম (অ্যাপ সার্ভার) নয় — তাই বেশি ওয়েটার নিয়োগে লাভ নেই। Thundering herd হলো জনপ্রিয় পদ শেষ হওয়ার মুহূর্তে চল্লিশ ওয়েটারের একসাথে রান্নাঘরে হানা — সমাধান: একজন রাঁধবে, বাকিরা বলবে 'দুই মিনিট' (লক, পুরনোটা দিন)।

ধারণাটি সংক্ষেপে

লোড বাড়লে যে ক্রমে জিনিস ভাঙে: প্রথমে ডেটাবেজ কানেকশন ও ধীর কোয়েরি, তারপর ক্যাশ মিস, তারপর কিউ জমে যাওয়া, তারপর স্টোরেজ ও ব্যান্ডউইথ। সমাধানও একই ক্রমে: ইনডেক্স ও কোয়েরি ঠিক করা, ক্যাশ, কানেকশন পুলিং, স্টেটলেস সার্ভার বাড়ানো, read replica, সবশেষে sharding। মনে রাখবেন replica-তে replication lag থাকে, তাই নিজের করা পরিবর্তন সাথে সাথে replica থেকে পড়বেন না। ক্যাশিংয়ে thundering herd সমস্যা: জনপ্রিয় কী মেয়াদ শেষ হলে হাজার রিকোয়েস্ট একসাথে মিস করে — লক দিয়ে একটিকে রিফ্রেশ করতে দিন।

The order things break under load — know this sequence and you can answer "your traffic 10x's tomorrow" instantly. Database connections and slow queries first. Then cache misses. Then queue backlog. Then storage and bandwidth. The application servers are usually last, because they are stateless and easy to add.

Fixes in the same order: indexes and query fixes, caching, connection pooling, horizontally scale stateless app servers, read replicas, and sharding last and reluctantly.

Read replicas come with replication lag, so do not read your own writes from a replica — a user who updates their profile and immediately sees the old version will report it as a bug.

Caching strategies — cache-aside (read through, the default), write-through (write to cache and store together), write-behind (fast, risky). The hard part is always invalidation: TTL where staleness is tolerable, event-based where accuracy matters, versioned keys to invalidate a group. Name the thundering herd problem — when a hot key expires and a thousand requests all miss simultaneously — and its fix, a lock so one request repopulates while others wait or serve stale.

Asynchronous architecture — queues decouple producers from consumers and absorb spikes. At-least-once delivery means consumers must be idempotent. Dead-letter queues catch poison messages. The outbox pattern solves the dual-write problem: write the event to a table in the same transaction as the state change, then publish separately.

Example
// Cache-aside with thundering-herd protection
async function getDashboard(tenantId) {
  const key = `dash:${tenantId}`;
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);

  // only one request rebuilds; others wait briefly and re-read
  const lock = await redis.set(`${key}:lock`, '1', 'NX', 'EX', 10);
  if (!lock) {
    await sleep(50);
    return getDashboard(tenantId);
  }
  try {
    const data = await buildDashboard(tenantId);      // expensive
    await redis.set(key, JSON.stringify(data), 'EX', 300);
    return data;
  } finally {
    await redis.del(`${key}:lock`);
  }
}

  await tx.order.update({ where: { id }, data: { status: 'paid' } });
  await tx.outbox.create({ data: {
    type: 'order.paid', payload: { orderId: id }, publishedAt: null,
  }});
});

Hold হলো সিনেমার সিট বাছাই: সিট ধরলেই অন্য সবার কাছে দশ মিনিট হলুদ, আপনি ততক্ষণে টাকা দেন। Hold না থাকলে দুই পরিবার F সারির ৭ নম্বর কেনে — একজন সিনেমা দেখে, আরেকজন রিফান্ড নিয়ে আর ফেরে না। আর মেয়াদ থাকে কোয়েরিতেই ('মেয়াদোত্তীর্ণ hold বাদ'), তাই পরিষ্কারের ছেলে ঘুমিয়ে পড়লেও পুরনো hold নিজে নিজেই খালি হয়।

ধারণাটি সংক্ষেপে

এটি আপনার নিজের ডোমেইন, তাই এটিই আপনার সবচেয়ে শক্তিশালী ডিজাইন উত্তর হওয়া উচিত। ডেটা মডেল: Resource, Availability, Hold (expires_at সহ), Booking, Payment, এবং অডিটের জন্য append-only BookingEvent। Hold অংশটি বেশিরভাগ প্রার্থী বাদ দেয় অথচ এটিই মূল — পেমেন্ট নেওয়ার আগে স্লট সংরক্ষণ করতে হবে, নইলে এমন স্লটের জন্য টাকা নেওয়া হবে যা আর পাওয়া যাবে না। availability কোয়েরি শুধু মেয়াদ-উত্তীর্ণ নয় এমন hold বাদ দেয়, তাই ক্লিনআপ জব সময়মতো না চললেও সমস্যা হয় না। পেমেন্ট নিশ্চিত করুন শুধুমাত্র যাচাইকৃত webhook থেকে, ক্লায়েন্ট রিডাইরেক্ট থেকে নয়।

This is your home domain, so it should be your strongest design answer. Structure it the way the round expects.

Clarify: how many resources and bookings per day, is double-booking absolutely forbidden or recoverable, do we handle payment, is there a cancellation window, single or multi-tenant.

Data model: Resource, Availability (rules or slots), Hold (with expires_at), Booking, Payment, and an append-only BookingEvent for audit. The hold is the piece most candidates miss and it is the heart of the design — you must reserve the slot *before* taking payment, or you charge people for slots they cannot have.

The core flow: check availability → create a hold with a short expiry → take payment → confirm booking on verified webhook → release the hold. If payment fails or times out, the hold expires by itself and the slot returns to the pool.

Concurrency: availability queries exclude unexpired holds, so expiry is automatic at read time rather than dependent on a cleanup job running on schedule. The write path takes a row lock or relies on a unique constraint on (resource_id, slot_start).

Payments: never confirm from a client redirect. Webhook is the source of truth, verified by signature, deduplicated on the provider's event id, processed idempotently.

Failure cases to raise unprompted: webhook arrives before the redirect, payment succeeds but the slot was taken (refund automatically, with a defined path), and the provider retries a webhook days later.

Example
-- The hold is the heart of the design
CREATE TABLE holds (
  id           BIGINT PRIMARY KEY,
  resource_id  BIGINT NOT NULL,
  slot_start   TIMESTAMPTZ NOT NULL,
  expires_at   TIMESTAMPTZ NOT NULL,
  session_id   TEXT NOT NULL,
  UNIQUE (resource_id, slot_start)          -- DB refuses a second hold
);

-- Availability excludes only UNEXPIRED holds: expiry is automatic at read time
SELECT s.slot_start
FROM slots s
LEFT JOIN holds h
       ON h.resource_id = s.resource_id
      AND h.slot_start  = s.slot_start
      AND h.expires_at  > now()
LEFT JOIN bookings b
       ON b.resource_id = s.resource_id
      AND b.slot_start  = s.slot_start
      AND b.status <> 'cancelled'
WHERE s.resource_id = :id
  AND h.id IS NULL
  AND b.id IS NULL;

-- Payment confirmation: webhook only, idempotent, signature-verified
-- 1. verify signature
-- 2. if processed_events has event_id → return 200, do nothing
-- 3. insert processed_events + confirm booking, in ONE transaction
-- 4. return 200 fast; heavy work goes to a queue

Availability queries exclude only unexpired holds, so expiry is automatic at read time and doesn't depend on a cleanup job. The write path is protected by a row lock plus a unique constraint on resource-and-slot. Layering, DDD-lite, and knowing when not to

Picture it like this

Layers are a hospital: the surgeon (domain) never fills insurance forms; reception (API) never prescribes. Everyone can be replaced without retraining the others — that's dependency pointing inward. But building a full hospital for a scraped knee (CRUD app) is over-engineering; sometimes a pharmacy visit (MVC plus a service class) is the correct medicine.

স্তরগুলো হাসপাতালের মতো: সার্জন (domain) বীমার ফর্ম পূরণ করেন না; রিসেপশন (API) ওষুধ লেখে না। প্রত্যেককে অন্যদের নতুন করে না শিখিয়েই বদলানো যায় — এটিই ভেতরমুখী নির্ভরতা। কিন্তু হাঁটু ছিলে যাওয়ার জন্য পুরো হাসপাতাল বানানো (CRUD অ্যাপে full layering) বাড়াবাড়ি; কখনো ফার্মেসিই (MVC + সার্ভিস ক্লাস) সঠিক চিকিৎসা।

ধারণাটি সংক্ষেপে

স্তরগুলো: Domain (ব্যবসায়িক নিয়ম, কোনো ফ্রেমওয়ার্ক নেই), Application (ইউজ কেস, ট্রানজেকশন), Infrastructure (ডেটাবেজ, বাইরের API), Web (কন্ট্রোলার)। নির্ভরতা ভেতরের দিকে যায়। সুবিধা: ডেটাবেজ ছাড়াই ব্যবসায়িক লজিক টেস্ট করা যায়। অসুবিধা: বেশি ফাইল, বেশি সময়। সবচেয়ে ভালো উত্তর ভারসাম্য দেখানো — সাধারণ CRUD অ্যাপে এই কাঠামো অতিরিক্ত। ছোট টিমের জন্য microservices নয়, modular monolith সঠিক; আলাদা সার্ভিস তখনই যখন কোনো অংশের স্কেলিং বা নির্ভরযোগ্যতার চাহিদা সত্যিই আলাদা — যেমন LLM সার্ভিস।

The layers: Domain (entities, value objects, business rules — no framework, no database, no HTTP), Application (use cases orchestrating the domain; transactions start here), Infrastructure (persistence, external APIs, storage, email), Web/API (controllers, request/response mapping, auth wiring). Dependencies point inward, achieved by defining interfaces in the inner layers and implementing them in the outer ones.

The honest trade-off is what makes this a senior answer. Benefits: domain logic testable without a database, and swapping the ORM or mail provider is a local change. Costs: more files, more indirection, slower initial development. For a CRUD-heavy product, Laravel's default MVC plus service classes is frequently correct, and saying so is a strength.

Interviewers are suspicious of candidates who believe one architecture fits everything. The best answer names the context: "the recruitment domain had real rules — interview configuration, scoring, workflow state — so layering paid off. For a straightforward admin panel I would not do it."

Monolith vs microservices for a small team: modular monolith. Microservices buy independent deployment and scaling in exchange for distributed transactions, network failure modes, and operational burden a five-person team cannot absorb. Extract a service only when one part has a genuinely different scaling or reliability profile — which is exactly the argument for putting LLM work in its own service.

Hexagonal/ports-and-adapters is the same idea with different vocabulary: the domain defines ports, infrastructure provides adapters.

Example
<?php
// Domain — no framework, no database, fully testable
final class Interview {
    public function __construct(
        private InterviewId $id,
        private CandidateId $candidate,
        private Rubric $rubric,
        private InterviewStatus $status,
    ) {}

    public function score(array $answers, Scorer $scorer): Score {
        if ($this->status !== InterviewStatus::Completed) {
            throw new InterviewNotCompleted();      // a business rule, not a DB rule
        }
        return $scorer->score($answers, $this->rubric);
    }
}

// Application — orchestrates, owns the transaction
final class ScoreInterviewHandler {
    public function __construct(
        private InterviewRepository $interviews,   // interface defined inward
        private Scorer $scorer,                    // interface: LLM lives outside
    ) {}

    public function handle(ScoreInterviewCommand $cmd): void {
        $interview = $this->interviews->get($cmd->interviewId);
        $score = $interview->score($cmd->answers, $this->scorer);
        $this->interviews->save($interview->withScore($score));
    }
}
// Infrastructure implements InterviewRepository (EF Core / Eloquent) and Scorer (HTTP → Python service)
Say this in the interview

I layer when the domain has real rules: domain at the centre with no framework, application services orchestrating use cases, infrastructure outside, dependencies pointing inward via interfaces — which made the recruitment platform's scoring logic testable without a database. But I say the cost out loud too: more files, slower CRUD. For a simple admin panel I'd use plain MVC with services, and for a five-person team a modular monolith beats microservices — extract a service only when something has genuinely different scaling needs, which is exactly why the LLM work lived in its own service.

How a recruiter tests this

'Explain the architecture you used and why' — then the challenge: 'wasn't that over-engineering?' Both-sides answers win; dogma loses.

Your drill

Draw your AI platform's layers from memory, then explain aloud one place the layering cost you time. Having that answer ready is what makes the rest credible.

Security, testing, and operating in production

Picture it like this

IDOR is a hotel where the receptionist checks your ID at the entrance but every room key opens every room — checking WHO you are is not checking WHAT is yours. And 'mitigate before diagnose' is firefighting: when the kitchen is burning you put the fire out FIRST and investigate the wiring after — rollback now, root-cause later.

IDOR হলো এমন হোটেল যেখানে রিসেপশনে আইডি দেখা হয় কিন্তু যেকোনো চাবিতে যেকোনো রুম খোলে — আপনি কে তা যাচাই করা মানে কোনটি আপনার তা যাচাই নয়। আর 'আগে সমাধান, পরে কারণ' হলো আগুন নেভানোর নিয়ম: রান্নাঘরে আগুন লাগলে আগে নেভান, ওয়্যারিং তদন্ত পরে — আগে rollback, পরে root cause।

ধারণাটি সংক্ষেপে

নিরাপত্তায় সবচেয়ে বড় বাস্তব সমস্যা broken access control — ইউজার কে তা যাচাই হয় কিন্তু এই ডেটা তার কিনা তা হয় না। URL-এ আইডি বদলে অন্যের অর্ডার দেখা গেলে সেটিই এই সমস্যা। প্রতিটি অবজেক্ট অ্যাক্সেসে সার্ভারে অনুমোদন যাচাই করুন এবং প্রতিটি কোয়েরি মালিক বা টেন্যান্ট দিয়ে স্কোপ করুন। এরপর: SQL injection (সবসময় parameterized query), XSS (আউটপুট escape), CSRF, সিক্রেট ভল্টে রাখা, SSRF (ইউজারের দেওয়া URL fetch করলে allowlist), ফাইল আপলোড যাচাই। টেস্টিংয়ে সবচেয়ে গুরুত্বপূর্ণ: অন্য ইউজারের ডেটা দেখা যায় কিনা তার টেস্ট। প্রোডাকশন সমস্যায় নিয়ম: আগে সমাধান, পরে কারণ খোঁজা।

Security — the eight that matter. Broken access control is number one in the real world: authentication usually works, authorization quietly does not. IDOR means /orders/123 returns someone else's order because you checked who they are but not whether the object is theirs. Fix by authorizing every object access server-side and scoping every query by owner or tenant.

Then: SQL injection (parameterized queries always; whereRaw with user input is the hole), XSS (escape on output; {!! !!} and v-html and dangerouslySetInnerHTML are the exceptions), CSRF (tokens plus SameSite for cookie auth), secrets (a vault, never the repo, APP_DEBUG=false), SSRF (allowlist hosts when fetching user-supplied URLs — directly relevant to scraping work), file uploads (validate type and size, store outside the webroot, randomize names), and dependency auditing in CI.

Testing strategy — many fast unit tests for pure logic, a strong layer of feature tests hitting your API, few E2E tests for critical flows. Fake at the boundary. The authorization test — can user A fetch user B's record — is the one that actually protects production. On coverage, say you test the money paths, the authorization rules, and the logic that fails silently, rather than chasing a number.

Operating — structured logs with correlation IDs, error tracking, metrics, traces. "Logs tell you what happened, metrics tell you something is wrong, traces tell you where." Incidents: detect, assess impact, mitigate before diagnosing, communicate, then a blameless post-mortem with one concrete prevention.

Example
<?php
// The vulnerability that actually breaches production
public function show(int $id) {
    return Order::findOrFail($id);          // BROKEN: any user, any order
}

public function show(Order $order) {
    $this->authorize('view', $order);       // policy checks tenant AND owner
    return new OrderResource($order);
}

// The test that protects it
it('does not leak another tenant\'s order', function () {
    $mine   = User::factory()->create(['tenant_id' => 1]);
    $theirs = Order::factory()->create(['tenant_id' => 2]);

    $this->actingAs($mine)
         ->getJson("/api/orders/{$theirs->id}")
         ->assertNotFound();                // 404, not 403 — don't confirm existence
});

// SSRF guard when fetching a user-supplied URL (scraping, webhooks, imports)
$host = parse_url($url, PHP_URL_HOST);
$ip = gethostbyname($host);
if (filter_var($ip, FILTER_VALIDATE_IP, FILTER_FLAG_NO_PRIV_RANGE|FILTER_FLAG_NO_RES_RANGE) === false) {
    throw new UnsafeUrlException();          // blocks 127.0.0.1, 169.254.169.254, 10.x
}

The vulnerability that actually breaches production is broken access control: authentication passes, but nobody checked the object belongs to the requester. So every object access goes through a policy, every query is tenant-scoped by default, and my favourite test is the one where user A requests user B's record and gets a 404 — not 403, so existence isn't confirmed. In an incident, I mitigate before diagnosing: rollback or feature-flag first, communicate, then root-cause into a blameless post-mortem with one concrete prevention.

How a recruiter tests this

'How do you stop a user reading another user's data?' and 'what do you test?' Also 'walk me through a production incident' — 'mitigate before diagnose' is the phrase they wait for.

Your drill

ধারণাটি সংক্ষেপে

প্রতিটি রাউন্ড কী মাপে তা জানলে প্রস্তুতি বদলে যায়। রিক্রুটার স্ক্রিন: যোগাযোগ, বেতন, নোটিশ, টাইমজোন — এখানে বেশি কথা বললেই হারবেন। টেকনিক্যাল স্ক্রিন: আপনার CV সত্যি কিনা। লাইভ কোডিং: চাপের মধ্যে আপনি কীভাবে ভাবেন — শেষ করা জরুরি নয়, চুপ থাকা সবচেয়ে বড় ভুল; সমস্যাটি আবার বলুন, ইনপুট ও এজ কেস জিজ্ঞেস করুন, আগে সহজ সমাধান লিখুন। টেক-হোম: তদারকি ছাড়া আপনার কোড কেমন — সময়সীমা মানুন, টেস্ট দিন, README-তে সিদ্ধান্ত ব্যাখ্যা করুন, অতিরিক্ত ইঞ্জিনিয়ারিং করবেন না। সিস্টেম ডিজাইন: আপনি সিস্টেমের মালিক হতে পারেন কিনা। বিহেভিয়ারাল: আপনার সাথে কাজ করা সহজ কিনা।

Understanding what each round *measures* changes how you prepare for it.

Recruiter screen (20–30 min). Measures: communication, salary fit, notice period, timezone, and whether your CV is real. Prepare: a 90-second story, your range, availability, and your overlap hours stated proactively. This round is lost by rambling, not by technical gaps.

Technical screen (45–60 min). Measures: whether your CV is true. Expect rapid questions across your listed stack and a small coding task. Prepare: the question banks, and be able to speak about every technology you listed.

Live coding (60 min). Measures: how you think under observation, not whether you finish. Restate the problem, ask about inputs and edge cases, narrate your approach before typing, write the simple version, test aloud with an example, then discuss improvements. Silence is the failure mode.

Take-home. Measures: what your production code looks like unsupervised. Respect the time-box, include tests, write a README explaining decisions and trade-offs, handle errors and empty states. Do not over-engineer — matching solution to problem is what is being tested.

System design (45–60 min). Measures: whether you can own a system. Clarify, then API and data model, then architecture, then bottlenecks, then trade-offs.

Behavioral / hiring manager. Measures: will you be a net positive on a team of five people who work with you daily. Have eight STAR stories written.

LIVE CODING — the script that keeps you out of trouble

1. RESTATE      "So I need a function that takes X and returns Y — is that right?"
2. CLARIFY      "Can the input be empty? Are duplicates possible? How large?"
3. APPROACH     "I'll use a hash map so lookups are O(1) instead of a nested loop.

4. CODE ALOUD   "I'm iterating once, and for each item checking whether the

6. COMPLEXITY   "O(n) time, O(n) space. The trade-off is memory for speed."
7. IMPROVE      "If the input were sorted I could do two pointers with O(1) space."

// Group orders by customer, sum totals, top 5 — one pipeline
$top = collect($orders)
    ->groupBy('customer_id')
    ->map(fn($group) => [
        'customer' => $group->first()['customer_name'],
        'total'    => $group->sum('amount'),
        'count'    => $group->count(),
    ])
    ->sortByDesc('total')
    ->take(5)
    ->values();

// Flat list with parent_id → tree (asked constantly)
function buildTree(array $items, ?int $parentId = null): array {
    $branch = [];
    foreach ($items as $item) {
        if ($item['parent_id'] === $parentId) {
            $children = buildTree($items, $item['id']);
            if ($children) $item['children'] = $children;
            $branch[] = $item;
        }
    }
    return $branch;
}

The web layer — HTTP, CORS, cookies, caching headers

Picture it like this

৪০১ বনাম ৪০৩ হলো ক্লাবের দরজা: ৪০১ মানে 'আইডি দেখান' — আপনি কে প্রমাণ হয়নি; ৪০৩ মানে 'চিনি আপনাকে, কিন্তু লিস্টে নাম নেই।' কুকির তিন ফ্ল্যাগ ব্যাংক লকার: httpOnly — কেরানি (JavaScript) খুলতে পারে না; secure — শুধু সাঁজোয়া গাড়িতে (HTTPS) যায়; sameSite — বাইরের কেউ আপনার লকার নম্বর দিয়ে নির্দেশ পাঠাতে পারে না (CSRF)।

ধারণাটি সংক্ষেপে

ফ্রেমওয়ার্কের নিচের এই স্তরটি সিনিয়রদের জানা ধরে নেওয়া হয়। ৪০১ মানে আপনি কে জানি না, ৪০৩ মানে জানি কিন্তু অনুমতি নেই — এ দুটি গুলিয়ে ফেলা সাধারণ ভুল। ৪০০ মানে ভাঙা রিকোয়েস্ট, ৪২২ মানে ভ্যালিডেশন ব্যর্থ। CORS ব্রাউজারের সীমাবদ্ধতা, সার্ভারের নিরাপত্তা নয় — curl দিয়ে যে কেউ API কল করতে পারে। কুকির তিনটি ফ্ল্যাগ মুখস্থ রাখুন: httpOnly (XSS টোকেন চুরি করতে পারে না — তাই localStorage নয়), secure (শুধু HTTPS), sameSite (CSRF ঠেকায়)। ক্যাশিং: হ্যাশ করা অ্যাসেট এক বছর immutable, ব্যক্তিগত ড্যাশবোর্ড no-store। GET idempotent, POST নয় — সেজন্যই পেমেন্টে idempotency key লাগে।

Framework knowledge sits on this layer, and seniors are expected to own it.

Status codes that carry meaning: 200/201/204; 400 (malformed) vs 422 (failed validation); 401 ("I don't know who you are") vs 403 ("I know, and you may not") — mixing these up is a classic tell; 404 also correct for objects a user must not know exist; 409 conflict; 429 with Retry-After; 500 vs 502 vs 504 (your code failed / upstream bad response / upstream timeout).

CORS is a browser restriction, not a server security feature. The browser blocks a page on origin A from *reading* a response from origin B unless B allows it. Anyone can still call your API with curl — so a CORS error never means your API is secure. Non-simple requests trigger a preflight OPTIONS; reject OPTIONS and everything breaks. Access-Control-Allow-Origin: * cannot be combined with credentials.

Cookies — the three flags you must recite: httpOnly (JavaScript cannot read it, so XSS cannot steal the session — this is why cookies beat localStorage for tokens), secure (HTTPS only), sameSite Lax/Strict (blocks the ambient cross-site request that makes CSRF possible).

Caching headers: Cache-Control (max-age, no-store, private/public), ETag + If-None-Match → 304. Hashed assets: max-age=31536000, immutable. A personalised dashboard: no-store. Being able to say which and why is a small answer that reads very senior.

Idempotent methods: GET/PUT/DELETE are; POST is not — which is exactly why idempotency keys exist for payment POSTs.

Example
// Session cookie done correctly — recite these three flags
res.cookie('session', token, {
  httpOnly: true,      // JS cannot read → XSS cannot steal
  secure: true,        // HTTPS only
  sameSite: 'lax',     // blocks the cross-site request CSRF needs
  maxAge: 3600_000,
});

// CORS with credentials: explicit origin required, '*' is invalid
app.use(cors({ origin: 'https://app.example.com', credentials: true }));

// Conditional request flow the interviewer may sketch:
// 1st:  GET /api/orders        → 200, ETag: "a3f9"
// 2nd:  GET /api/orders
//       If-None-Match: "a3f9"  → 304 Not Modified (empty body, bandwidth saved)

// Caching decisions, stated with reasons:
// app.8f3a1c.js  → Cache-Control: public, max-age=31536000, immutable
//                  (hash in the name = safe forever)
// /api/dashboard → Cache-Control: no-store   (personal, must be fresh)
// /api/products  → Cache-Control: private, max-age=60  (tolerable staleness)

401 means the server doesn't know who you are; 403 means it knows and you're not allowed — and I return 404 for objects a user shouldn't know exist. CORS is the browser refusing to hand a cross-origin response to JavaScript — it protects users, not the API, which curl reaches directly. Git beyond add/commit/push: stash (park work to switch context), rebase -i (squash before a PR), cherry-pick (hotfix backports), revert (undo safely on a shared branch — never reset --hard on anything pushed), blame and log -S (when and why a line changed), and bisect — binary search through history for the commit that broke things. Mentioning bisect marks real experience.

Merge vs rebase: merge preserves true history with a merge commit; rebase rewrites your commits onto the target for linear history. The rule: rebase your own unpushed branch, never a branch others have pulled.

Code review — as author: small PRs, a description explaining *why*, self-review first, tests included. As reviewer: comment on the code not the person, separate blocking issues from preferences (prefix nits), approve when it is better than what exists rather than perfect. For disagreements: escalate to a synchronous conversation quickly — a long thread means the disagreement is bigger than the code. Your mentoring at DevVoyage and L2N lives here; have one specific story.

Debugging is a method, not a talent, and "your hardest bug" is asked in nearly every senior loop. The method: reproduce reliably (most of the time goes here), minimize to the smallest failing case, hypothesize specifically enough to be provable false, instrument (logs, Xdebug, EXPLAIN, network tab — look at data, don't guess), change one thing, fix, then write the regression test, then ask why it wasn't caught. Structure the story: symptom → what I suspected → how I narrowed it → root cause → fix → prevention. The prevention step is what sounds senior.

// Webhook handler — the three steps, in this order, every time
public function handle(Request $request)
{
    // 1. Signature FIRST — never touch the payload before this
    abort_unless($this->verifySignature($request), 401);

    $eventId = $request->input('event_id');

    // 2. Deduplicate — providers retry for days
    if (ProcessedEvent::whereEventId($eventId)->exists()) {
        return response()->noContent();      // already handled: 2xx, do nothing
    }

    // 3. Record + transition in ONE transaction, heavy work queued
    DB::transaction(function () use ($request, $eventId) {
        ProcessedEvent::create(['event_id' => $eventId]);

        $payment = Payment::whereReference($request->input('reference'))
            ->lockForUpdate()->firstOrFail();

        $payment->transitionTo(          // state machine rejects illegal moves
            PaymentStatus::from($request->input('status'))
        );
    });

    SettlePaymentSideEffects::dispatch($eventId)->afterCommit();
    return response()->noContent();      // fast 2xx so they stop retrying
}

// The state machine that stops a late webhook un-refunding an order
public function transitionTo(PaymentStatus $to): void {
    $legal = match($this->status) {
        PaymentStatus::Pending    => [PaymentStatus::Authorized, PaymentStatus::Failed],
        PaymentStatus::Authorized => [PaymentStatus::Captured, PaymentStatus::Failed],
        PaymentStatus::Captured   => [PaymentStatus::Settled, PaymentStatus::Refunded],
        default                   => [],   // terminal states accept nothing
    };
    if (! in_array($to, $legal)) throw new IllegalTransition($this->status, $to);
    $this->update(['status' => $to]);
}

ধারণাটি সংক্ষেপে

খুব কম প্রার্থী এটি নিয়ে বিশ্বাসযোগ্যভাবে কথা বলতে পারে — তাই এটিই আপনার সবচেয়ে স্মরণীয় গল্প। স্থাপত্য চার অংশে: local-first লেখা (সব পরিবর্তন আগে IndexedDB-তে, UI নেটওয়ার্কের জন্য অপেক্ষা করে না), outbox (অপেক্ষমাণ কাজ, প্রতিটিতে ক্লায়েন্ট-জেনারেটেড আইডি), ব্যাকগ্রাউন্ড সিঙ্ক, আর reconciliation। কনফ্লিক্টে সবচেয়ে শক্তিশালী উত্তর: ডোমেইন এমনভাবে ডিজাইন করা যাতে কনফ্লিক্ট হতেই না পারে — বিক্রয় append-only, দুই ডিভাইসের বিক্রয় সাংঘর্ষিক নয়, দুটোই ঘটেছে। যে বিবরণগুলো প্রমাণ করে আপনি এটি বানিয়েছেন: idempotency (রিপ্লে হলে ডুপ্লিকেট নয়), ordering (ডিভাইস-প্রতি সিকোয়েন্স), clock skew (ডিভাইসের ঘড়ি ঘণ্টার হিসেবে ভুল হয় — সার্ভার টাইম ব্যবহার), আংশিক ব্যর্থতা, এবং লোকাল স্কিমা মাইগ্রেশন — প্রোটোকলকে এক ভার্সন পেছনের ডিভাইস সহ্য করতে হয়। ছয় মিনিটের সংস্করণ ছবি এঁকে মুখস্থ করুন।

Very few candidates can discuss this credibly, which makes it your most memorable technical story. It deserves more rehearsal than anything else you own.

Why: a point of sale that stops when the internet drops is worthless to a shop, so the device must be authoritative during an outage and the server reconciles afterwards.

The architecture, in four pieces. Local-first writes — every mutation hits IndexedDB immediately, so the UI never waits for the network. An outbox — pending operations queue locally, each carrying a client-generated ID. Background sync — a process drains the outbox on reconnect; the server responds with authoritative state. Reconciliation — the client applies server state and resolves divergence.

Conflicts — the part they will probe. Last-write-wins is simple and silently deletes someone's sale. Per-field server-authoritative merge works for edits. But the strongest answer is modelling conflicts away: a sale is append-only, so two devices creating sales don't conflict — both happened, the total is the sum. Design the domain so most conflicts cannot exist, and arbitrate only the rest.

The details that prove you built it: idempotency (the client ID makes a replayed sync a no-op rather than a duplicate sale); ordering (per-device sequence numbers so operations apply causally); clock skew (device clocks lie by hours — anything authoritative uses server time or logical ordering); partial failure (operations drain individually; never mark a batch synced when only part succeeded); and local schema migration — the hard operational problem: the client stores a schema version, migrates local data on upgrade, and the protocol tolerates a device one version behind, because you cannot force every device to update before it reconnects.

Rehearse the six-minute version with a drawing: problem → four-piece architecture → the conflict decision and why append-only → one failure you hit → what you'd change.

Example
// The outbox — every operation self-identifying and replayable
// IndexedDB: outbox
{ opId: "dev7-000142",            // device prefix + per-device sequence
  type: "sale.created",
  payload: { saleId: "s-8f31", items: [...], total: 45000 },
  deviceSeq: 142,
  clientTime: "2026-08-20T14:02:11+06:00",   // display only — never authoritative
  synced: false }

// Drain: individually, in order, tolerant of partial failure
async function drainOutbox() {
  const pending = await db.outbox.where('synced').equals(false)
                                 .sortBy('deviceSeq');
  for (const op of pending) {
    try {
      const res = await api.post('/sync/ops', op);   // server: opId seen? → no-op,
      await db.outbox.update(op.opId, {              // return original result
        synced: true, serverState: res.state
      });
    } catch (e) {
      if (isRetryable(e)) break;      // stop HERE — later ops wait, order holds
      await flagForReview(op, e);     // poison op: park it, don't block the queue
    }
  }
}

// Server side, the idempotent receiver:
// INSERT INTO processed_ops (op_id) ... ON CONFLICT DO NOTHING
// → if conflict: fetch and return the original result. Replay is free.

// Conflicts designed away: sales are append-only.
// Two devices, two sales, no conflict — both happened. SUM() is the truth.
Say this in the interview

The shop must keep selling when the internet drops, so the device is authoritative during the outage: writes land in IndexedDB instantly, queue in an outbox with client-generated IDs and per-device sequence numbers, and a background process drains them on reconnect — individually, so partial failure never marks unsent work as synced. Replay is free because the server treats a seen ID as a no-op. And the best conflict resolution was modelling conflicts away: sales are append-only, two devices creating sales both happened. Device clocks lie by hours, so nothing authoritative trusts client time.

How a recruiter tests this

'How does your offline sync work?' then straight to conflicts, replay, and clock skew. This is where you can be better than every other candidate — or vague, which is worse than not claiming it.

Your drill

Record yourself explaining the sync for six minutes with a hand-drawn diagram. Listen back: every hedge marks a decision you haven't actually made. Decide it, re-record.

সিনিয়র লেভেলে টেকনিক্যাল দক্ষতা ধরে নেওয়া হয়; বিহেভিয়ারাল রাউন্ডে প্রশ্ন হলো — পাঁচজনের টিমে প্রতিদিন আপনার সাথে কাজ করা সহজ হবে কিনা। STAR নিয়ম: পরিস্থিতি দুই বাক্যে, আপনার কাজ চার-পাঁচ বাক্যে ("আমি" বলুন, "আমরা" নয়), ফলাফল ও শিক্ষা — মোট দুই মিনিটের কম। আটটি গল্প আগে লিখে রাখুন: কঠিনতম বাগ, মতবিরোধ, প্রোডাকশন ভাঙা, মেন্টরিং, ডেডলাইনের খারাপ খবর আগে জানানো, কঠিন ফিডব্যাক নেওয়া, ভুল ট্রেড-অফ। প্রাক্তন নিয়োগকর্তার সমালোচনা কখনো নয়। অফারের আগে তিনটি সংখ্যা ঠিক করুন: লক্ষ্য, গ্রহণযোগ্য, প্রত্যাখ্যান-সীমা। কলে কখনো সাথে সাথে গ্রহণ করবেন না — এক-দুই দিন সময় চান। পুরো প্যাকেজ দেখুন: কারেন্সি, বাংলাদেশে পেমেন্টের পদ্ধতি, নোটিশ পিরিয়ড, ছয় মাসে রিভিউ (লিখিতভাবে চান)।

The behavioral round decides more senior offers than candidates believe, because at this level technical competence is assumed and the question becomes: is this person a net positive on a team of five who work with them daily?

STAR discipline: Situation and Task in two sentences, Action in four or five (what *you* did — say "I", not "we"), Result in one or two, plus the lesson. Under two minutes total. Write eight stories before your first loop: hardest bug (use the six-step debugging structure), a disagreement where you argued then committed, a time you broke production, mentoring someone concrete, delivering bad news about a deadline early, pushing back on scope, receiving hard feedback and changing, and a trade-off you got wrong. The last two matter most — they test whether you can be honest about imperfection, and defensiveness there is disqualifying. Never criticise a former employer or colleague: the interviewer can't verify the story, but they can observe how you talk about people who aren't in the room.

Your specific landmines, prepared not improvised: why the contract ended (two calm sentences, references offered, stop talking); the AI question (I own the design, AI accelerates the typing, I ship nothing I can't explain); CoreBari (a product I built, largely automated, doesn't compete with working hours); timezone (a year of evidence, stated overlap window).

The offer. Decide three numbers before the first call: target, acceptable, walk-away. When asked expectations early, ask for their range first; if pressed, give yours as a range anchored at target. Never accept on the call — thank them, ask for a day or two, and use any competing process as gentle leverage stated honestly. Evaluate the whole package: currency, payment mechanics for Bangladesh, contractor vs employee status, notice period, review cycle. A slightly lower offer with a real review at six months can beat a higher one with none — ask for the review in writing.
