FROM YOUR CV — 'Owned the AI recruitment product end to end'

05Walk me through that platform — architecture, not features.

Why they askThe core system-design question of your interview. They want to see whether you were the owner or a passenger.

Say your answer out loud first — then reveal
The product automates early-stage recruitment. A recruiter posts a job, candidates apply and upload CVs, the system parses and stores them, an AI conducts a structured first interview, and the platform scores and returns feedback. Architecturally it's a React/Next.js frontend against an ASP.NET Core Web API, with EF Core over Azure SQL. The LLM work — CV scoring in particular — runs as a separate Python service, so the model-facing code stays isolated from the transactional backend and can change without redeploying the API. Slow work runs in the background rather than in a request. The backend is layered: domain rules in the centre, application services orchestrating use cases, infrastructure holding EF Core and the external API clients, and the Web API on the outside. Follow-ups to expect
Draw the data model.
Core entities: Job, Candidate, Application, CV/Document, Interview, InterviewQuestion/Response, Score, Feedback. Application joins Candidate and Job and carries workflow state. Scores hang off the Application with the rubric version, so you can re-score without losing history.
Where would this break first under load?
The LLM calls — slowest and most rate-limited, so the queue backs up there first. Then database connections during bulk CV imports. The API itself is least likely, because the heavy work is already off the request path.
What would you change if you rebuilt it?
Define the scoring contract between the C# API and the Python service more strictly from day one — a versioned schema — because that boundary was where most integration friction lived.
TrapHave a diagram ready on paper. If you only describe features, you sound like a user of the system rather than its architect.
FROM YOUR CV — 'AI-conducted interviews, scoring, and feedback' + Python LLM service

06How did you make an unreliable model behave predictably in production?

Why they askThis separates people who called an API from people who engineered around one. It is your strongest differentiator in 2026.

Say your answer out loud first — then reveal
The hard part wasn't calling the model — it was making a non-deterministic component safe inside a transactional system. I kept it in a separate Python service so the boundary was explicit: the C# API sends a scoring request, the Python service owns prompts, model calls and parsing, and returns a validated result. Three things mattered. First, structured output: I asked for JSON against a defined schema and validated it on the way back, rather than parsing prose with regex; if validation failed the job retried and eventually flagged for human review instead of writing a bad score. Second, everything ran as a background job, because model calls take seconds and fail intermittently — so retries with backoff, and the job written to be safe to run twice. Third, grounding: scoring was against a defined rubric with the candidate's actual answers in context, not a free-form 'rate this person', which reduced drift between runs.
Follow-ups to expect
Why a separate Python service rather than calling the model from C#?
Two reasons. The Python ecosystem for model work is better — libraries, parsing, iteration speed — and isolating it meant I could change prompts and scoring logic without touching or redeploying the transactional API. It also kept the failure domain separate: if scoring degraded, the rest of the platform kept working.
How did you evaluate whether a prompt change made things better?
Be honest about the rigour you had. If it was a held-out set of CVs with known expected outcomes, say so. If it was systematic spot-checking against known-good cases before rollout, say that — inventing a formal eval harness you didn't build is a trap.
What did you do about hallucinated content?
Grounding and validation. Scores came from a fixed rubric with the actual answers in context, and outputs were schema-validated — anything outside the allowed shape was rejected rather than stored. Anything affecting a hiring decision produced input to a human, not a verdict.
How did you control cost?
Token accounting per request, tight prompts rather than stuffing whole documents, chunking long CVs, not re-scoring unchanged content, and cheaper models for mechanical extraction with the stronger one only where judgement was needed.
TrapDon't overclaim on evaluation rigour. If you didn't have a formal eval set, say what you did do — spot-checking against known cases is a legitimate answer.
FROM YOUR CV — 'CV processing' + Python LLM scoring service

07How did CV processing and scoring actually work, end to end?

Why they askA concrete pipeline question. They want detail, not a summary.

Say your answer out loud first — then reveal
Upload goes to cloud storage and a background job picks it up. Extract text, normalise it, then the Python service pulls structured fields — contact details, experience, skills — from the model against a schema, and separately scores the CV against the job's criteria. The parsed result and the score are stored alongside the raw file, so we never lose the original and a scoring improvement can be re-run over history. Failures are the interesting part: image-only PDFs, unusual layouts, multi-column CVs that extract in the wrong reading order. Those get flagged rather than silently stored wrong.
Follow-ups to expect
What formats gave you trouble?
Scanned or image-only PDFs with no text layer, multi-column layouts that extract in the wrong reading order, and CVs built in design tools where text order doesn't match visual order. The mitigation is detecting nonsensical extraction and flagging rather than scoring garbage.
How did you handle a CV that failed to parse?
It went to a failed state with the reason recorded and surfaced for human review, rather than silently producing a low score. Failing loudly matters — a silent zero looks like a real result.
Any privacy considerations with CV data?
Yes — CVs are personal data. Store only what the process needs, control access to candidate records, don't send more than necessary to a third-party model, and be able to delete a candidate's data on request. Worth raising before they ask.
TrapExpect a follow-up on personal data. Have a sentence ready about storing only what's needed and controlling access to candidate records.
FROM YOUR CV — 'Structured the backend in layers… Repository and Specification patterns'

08Why Specification? Wasn't that over-engineering?

Why they askA direct challenge to a named pattern. They're testing whether you chose it or copied it.

Say your answer out loud first — then reveal
It earned its place because candidate filtering was combined in many different ways across use cases — status, role, score threshold, date applied, interview stage — and those combinations kept changing. Without specifications the repository grows twenty near-identical methods that can't be tested independently. With them, each rule is an object I can compose and unit test on its own. Follow-ups to expect
When would you not use Repository at all?
In Laravel, most of the time — Eloquent is already an abstraction over the database, so wrapping it usually adds indirection without benefit. I'd use one when I genuinely need to swap the data source, or in strict DDD.
Did the layering ever slow you down?
Yes, on simple CRUD features where a change touched four files instead of one. That's the honest cost. It paid off on the parts with real rules — scoring, interview configuration, workflow state — and I'd make the same trade there, but not uniformly.
TrapNever defend a pattern on principle. Defend it on the specific problem it solved, and be willing to say where you wouldn't use it.

FROM YOUR CV — 'sending ran off the request cycle in jobs that were safe to retry'

10What does 'safe to retry' mean concretely? How did you make it idempotent?

Why they askYou put idempotency on your CV. They will check that you understand it rather than having heard the word.

Say your answer out loud first — then reveal
A worker can die after doing the work but before acknowledging it, so any job can run twice — that's normal, not exceptional. For email sending, the risk is emailing the same lead twice. So each send is keyed: before sending I check whether that lead-campaign pair has already been marked sent, and I record the send in the same transaction as the state change. Where possible I set a value rather than incrementing one, so a repeat is a no-op rather than a double count. The provider's own retry behaviour matters too, which is why the job returns fast and doesn't hold the request.
Follow-ups to expect
What if the email provider succeeds but your database write fails?
That's the dual-write problem and it's the honest hard case — you can't make two systems atomic. Record intent before sending so you can detect the gap, reconcile against the provider's delivery records, and accept at-least-once as the realistic guarantee.
How did you handle bounces?
Bounce and complaint feedback marks the address so it isn't retried — hard bounces suppressed permanently, soft bounces retried a limited number of times. Ignoring this destroys sender reputation, which is what actually kills a campaign platform.
What's a dead-letter queue for?
After a job exhausts its retry budget it goes to a dead-letter queue instead of retrying forever or vanishing. It parks the message where a human can inspect it, and stops one poison message consuming worker capacity indefinitely.
TrapThis is your best chance to sound genuinely senior. Rehearse it until it's fluent — it also transfers directly to any payments question.
FROM YOUR CV — 'deployed on Azure (Azure SQL, Key Vault) and Render with GitHub Actions'

11Walk me through your deployment pipeline. How do you deploy safely?

Why they askChecking that you've operated software, not just written it.

Say your answer out loud first — then reveal
The pipeline runs on push: install dependencies, run tests, then deploy on main. Secrets never live in the repo — they're in GitHub secrets and Azure Key Vault, pulled at runtime. On deploy order, the rule I follow is migrations first and only backward-compatible ones, so old code never meets a schema it doesn't understand; then the code; then cache and config; then restart background workers, because they hold the old code in memory until you do. Rollback is redeploying the previous build.
Follow-ups to expect
How do you do a zero-downtime column rename?
Expand and contract. Add the new column nullable and deploy. Deploy code writing to both. Backfill in batches. Switch reads. Drop the old column in a later release. Never rename in place while old code is running.
What's your rollback plan if a migration breaks?
That's why migrations must be backward-compatible — if the change is additive, rolling the code back is safe on its own. For destructive changes, backup first and test the down migration, but structure changes so rollback never requires undoing a migration under pressure.
How do you know a deploy succeeded?
Health check endpoint, error rate and latency watched for the first minutes after release, and a look at the logs for new exception types. 'It deployed without failing' isn't the same as 'it's working'.
TrapThe queue-worker restart detail is a strong signal — don't skip it. The expand/contract migration pattern is the expected answer to the follow-up.
FROM YOUR CV — Skills — 'JWT'

12How did you handle authentication? Why JWT?

Why they askAuth questions are near-universal, and JWT invites a revocation follow-up.

Say your answer out loud first — then reveal
The API used JWT with short-lived access tokens. The honest trade-off with JWT is that you can't un-issue a token, so revocation is the hard part — which is why the access token expiry is short and the refresh path is what you actually control. The signing secret lived in Key Vault rather than configuration. On the client side, tokens go in httpOnly cookies rather than localStorage, because localStorage is readable by any XSS.
Follow-ups to expect
How would you revoke a compromised token immediately?
You can't revoke the access token itself, so you shorten the window and control the refresh: revoke the refresh token server-side, and keep a denylist of token IDs checked per request if immediate revocation is a hard requirement. That reintroduces a lookup — the cost of true revocation with JWT.
Sanctum vs JWT — when would you pick each?
Sanctum for a first-party Laravel app — cookie auth for the SPA, simple revocable tokens for mobile, no OAuth ceremony. JWT when the token must be verified by multiple services without calling a central session store. If I don't need that, I don't take on JWT's revocation problem.
What's in a JWT payload?
Header, payload and signature, base64url-encoded. The payload is signed, not encrypted — anyone can read it, so no secrets go in it. You verify the signature and check expiry, issuer and audience, and reject 'alg: none'.
TrapNever say a JWT is encrypted. The payload is base64, readable by anyone — say so before they catch it.

FROM YOUR CV — 'booking flows covering availability, pricing, reservation, and checkout'

13How did you prevent double bookings?

Why they askThe classic domain question for anyone with booking systems on their CV. There is no way to bluff it.

Say your answer out loud first — then reveal
Concurrency on the slot is the whole problem — two requests can both read 'available' before either writes. Three ways to handle it. Pessimistic locking: SELECT … FOR UPDATE on the slot row inside a transaction, so the second request blocks until the first commits. A unique constraint on the resource-and-slot pair, so the database itself rejects the duplicate. Or optimistic locking with a version column and a retry on conflict. I lean on the database constraint wherever the model allows it, because it still holds even if a future developer forgets the application logic.
Follow-ups to expect
What happens when the payment succeeds but the slot was taken?
That's why the slot is held before payment rather than after — a reservation with a short expiry, so the seat is yours while you pay. If it still happens, the resolution is an automatic refund and a clear message, not silently keeping the money.
How do you handle holds that expire?
The hold carries an expiry timestamp and availability queries exclude only unexpired holds — so expiry is effectively automatic at read time rather than depending on a cleanup job running on time. A scheduled job tidies the rows afterwards.
What isolation level were you running?
MySQL/InnoDB defaults to Repeatable Read. That prevents non-repeatable reads within the transaction but does not by itself stop two transactions from both booking — which is exactly why you need the explicit lock or the unique constraint.
TrapDon't answer only 'I used a transaction'. A transaction alone does not prevent this — the lock or the constraint does.
FROM YOUR CV — 'integrated payment gateways… for booking and checkout'

14Walk me through a payment integration. What goes wrong?

Why they askThey want to know whether you've handled money in production or just called an SDK.

Say your answer out loud first — then reveal
The flow is: create the order in a pending state, hand off to the gateway, then confirm from a verified server-side signal — never from the client redirect, because the user can close the tab or the redirect can be forged. So the webhook is the source of truth: verify the signature first, then deduplicate on the provider's event ID because they retry aggressively, then process and return 2xx quickly with heavy work queued. Money is stored as integer minor units or decimal, never float. And the order stores the price at the time of purchase, because prices change and historical orders must not.
Follow-ups to expect
What if the webhook arrives before your redirect handler?
It regularly does, and the system has to be fine with it. Both paths converge on the same idempotent state transition keyed on the payment reference — whichever arrives first moves the order to paid, the second is a no-op. If order matters anywhere, that's a design bug.
How do you reconcile with the provider?
A scheduled job compares your records against the provider's for a period and reports discrepancies. They will diverge eventually — a missed webhook, a manual refund in their dashboard — and reconciliation is how you find out before your customer does.
How do you handle partial refunds?
The refund is its own record against the original payment rather than an edit to it, so history stays append-only and the net position is derivable. Never mutate or delete the original payment row.
Trap'Never trust the client redirect for payment confirmation' is the sentence that proves you've shipped payments. Say it explicitly.
FROM YOUR CV — 'Tuned MySQL schemas and queries against production booking data'

15Give me a specific query you optimised and how.

Why they askA specific claim invites a specific example. A generic answer here undermines the bullet.

Say your answer out loud first — then reveal
The recurring pattern was availability and booking listings that filtered on several columns and sorted by date. Two things dominated. First, N+1 — a listing looping over bookings and lazily loading customer or property on each, which I'd find in the query log or with Debugbar and fix by eager loading. Second, missing or wrongly ordered composite indexes: an index has to match the filter order, so an index on the tenant or property column first, then status, then date, with the range condition last. I'd confirm with EXPLAIN that it wasn't doing a full scan or a filesort rather than assuming.
Follow-ups to expect
What does EXPLAIN tell you?
Which index the optimiser chose, how many rows it expects to examine, and whether it's doing a full table scan, filesort or temporary table. The red flag is rows examined vastly exceeding rows returned. EXPLAIN ANALYZE gives actual timings.
When does an index not help?
Low-cardinality columns like booleans, leading-wildcard LIKE '%term', a function wrapped around the column such as YEAR(created_at), implicit type casts, and very small tables where a scan is cheaper anyway.
Why does OFFSET pagination get slow?
The database reads and discards every skipped row — page 1000 means reading 20,000 rows to return 20. Keyset pagination filters on 'id greater than the last seen value' and uses the index directly, so depth stops mattering.
TrapHave EXPLAIN vocabulary ready — full table scan, filesort, rows examined. If you can't read a plan aloud, this bullet becomes a liability.
FROM YOUR CV — 'Refactored legacy PHP into maintainable Laravel and Symfony code'

16How do you safely refactor code with no tests?

Why they askMost companies are hiring you for existing code. This question is really about risk judgement.

Say your answer out loud first — then reveal
You don't refactor code you can't verify, so the first step is characterisation tests — tests that capture the current behaviour, bugs included, so you know the moment you change it. Then small steps, always green, and never changing behaviour and structure in the same commit. For anything large I prefer the strangler approach: build the new path alongside the old, route part of the traffic to it, expand, then delete the old one — rather than a big-bang rewrite that leaves the system broken for weeks.
Follow-ups to expect
How do you decide what's worth refactoring?
Where change is frequent and painful. Ugly code nobody touches costs nothing; moderately messy code in the path of every new feature costs constantly. I follow change frequency, not aesthetic preference.
How do you sell a refactor to a manager?
In delivery terms: 'this coupling means a pricing change takes three days instead of three hours, and we've made two production mistakes because of it'. Then propose it incrementally alongside feature work, not as a project that pauses delivery.
TrapFor the manager follow-up, translate into delivery cost: 'this coupling means a pricing change takes three days instead of three hours'. Saying 'the code is ugly' loses the argument.

FROM YOUR CV — 'offline-first PWA synchronisation'

19How does the offline sync work? How do you resolve conflicts?

Why they askThe most technically impressive thing on your CV, and very few candidates can discuss it. Expect them to dig.

Say your answer out loud first — then reveal
The requirement is that a shop keeps selling when the internet drops, so the device has to be authoritative during an outage. Writes go to local storage immediately and queue in an outbox, so the UI never blocks on the network. A background process drains the outbox when connectivity returns and the server responds with authoritative state. Every operation carries a client-generated ID so a replayed sync doesn't duplicate a sale. On conflicts — the best answer is to model them away: a sale is append-only, so two devices creating sales don't actually conflict, they both happened. Where genuine divergence is possible I go server-authoritative per field. And device clocks lie, sometimes by hours, so anything authoritative uses server time rather than the device's.
Follow-ups to expect
What happens if the same device syncs twice?
Nothing, by design. Each operation carries a client-generated ID and the server treats a repeat as a no-op, returning the original result. Same idempotency principle as the payment and email work.
How do you migrate the local schema?
The genuinely hard operational problem. The client stores a schema version and runs migrations against local data on upgrade, and the sync protocol has to tolerate a device a version behind — you cannot force every device to update before it next connects.
What if a sync partially fails?
Operations drain individually rather than as one batch, so a failure stops that operation and leaves the rest of the outbox intact and retryable. What you must avoid is marking the whole batch synced when only part succeeded.
TrapPractise this until it's six confident minutes with a drawing. It's the single strongest technical story you own.
FROM YOUR CV — 'sharing one identity layer with single sign-on across apps'

20How does SSO across your apps work?

Why they askA natural follow-up, and multi-tenancy questions usually come with it.

Say your answer out loud first — then reveal
One identity service issues the session, and each app trusts it rather than holding its own users, so a user signs in once and moves between apps. Entitlements are separate from identity — which apps a tenant has access to comes from their subscription, checked per request. On tenancy, every record is scoped to a tenant and scoping is the default rather than something you opt into, because the top risk in a system like this is one forgotten filter leaking another business's data.
Follow-ups to expect
How do you guarantee no cross-tenant leakage?
By making scoping impossible to forget rather than relying on discipline — tenant context resolved once per request and applied by default, so an unscoped query is the exception you must write deliberately. Row-level security in the database is the stronger version.
What are the multi-tenancy options and why did you pick yours?
Shared table with a tenant column — cheapest, but one missed filter leaks data. Row-level security — enforcement in the database, safer. Schema per tenant — better isolation, migrations multiply. Database per tenant — strongest, heaviest. I chose shared with strict scoping because shared data across apps is the point of the suite.
TrapBe ready to name the four tenancy models — shared table with tenant ID, row-level security, schema per tenant, database per tenant — and the trade-off you accepted.

Follow-ups to expect
What's deferred execution?
A LINQ query over IQueryable isn't executed when written — it's translated to SQL and runs when you materialise it with ToList, First, Count. The bug is calling ToList too early, which pulls the whole table into memory and filters in C# instead of the database.
Explain DI lifetimes.
Transient is a new instance per resolution, scoped is one per request, singleton is one for the application's lifetime. The classic bug is injecting a scoped DbContext into a singleton — it captures one request's context forever and corrupts everything afterwards.
AsNoTracking — what and why?
EF Core tracks entities to detect changes on save. For read-only queries that tracking is pure overhead and memory, so AsNoTracking skips it. A straightforward win on list and report queries you'll never save.
TrapDo not inflate here. .NET interviewers probe internals within two questions, and an exposed bluff costs more than the honest boundary.
